1.1 화면 ① 종합 대시보드 (002135438.png)

레이아웃: 좌측 고정 사이드바 + 상단 바 + 본문 카드 그리드.

사이드바 (정보 구조가 그대로 드러남)

구분 메뉴 비고
캠퍼스 선택 현재 캠퍼스: 전병훈 수학학원 고등관 다중 캠퍼스 전환 UI (드롭다운)
ACADEMIC OPERATIONS 종합 대시보드 현재 화면
학생/반 관리 학생·클래스 CRUD
일일 수업 & 성적 입력 화면 ②
시험지 · 오답 분석 화면 ④
성적 통계 분석 캡쳐 없음 — 추정 필요
발송 내역 & 설정 문자 발송 로그·설정
카카오 알림톡 카카오 채널 발송
하단 위젯 알리고 문자 발송·연결 설정 잔여 발송량(장문 1,791건 / 단문 5,523건 / 이미지 773건), 잔액 조회 시각, 새로고침

상단 바: 날짜(오늘), 반 선택 드롭다운(고2 윤B), 학생 이름 검색, 알림, 도움말, 로그인 사용자(홍성윤 강사).

본문

영역 내용 데이터 출처
헤더 "DIRECTOR COMMAND MODE" 배지, 제목, 요약문("등록된 4개 반 · 47명"), 버튼: 오늘 수업 일괄 입력 / 상담일지 작성 / 다운로드 반·학생 집계
KPI 카드 4개 총 재원생 & 반 현황(47명, 활성 4개 반, 반별 명단 링크) / 선택한 반 등원 현황(4/13명, 출석+지각+조퇴 합산) / 금주 과제 완수율(93.8%, 전주 대비 +2.4%p, 미제출 5건, 재검사 대상 4명) / 주간테스트 종합 평균(82.6점, N=84, MAX 100(4명), MIN 58) 출결·과제·테스트 집계
반별 출결 체크 반·날짜 선택 → 학생별 [출석/지각/결석/조퇴] 토글 + 사유 입력, 하단 [확인]/[편집], 요약 카운트(미확인 9·출석 4·…) 출결 테이블
지난 수업 진도 & 과제 직전 수업일(09-18)의 교시별(1~4교시) 수업 내용, 과제 목록, "수업 기록 보기" 링크 수업일지 테이블

관찰 포인트: 출결 상태는 "미확인" 상태가 별도로 존재(입력 전 기본값). 이미 체크한 상태를 다시 누르면 해제. 확인 후 잠금 → 편집으로 해제하는 2단계 저장.

1.2 화면 ② 일일 수업 & 성적 입력 (002140176.png)

두 패널 구조: 좌측 = 반 전체 명단 그리드, 우측 = 선택 학생/반의 상세 입력.

상단 KPI: 등원 현황(4/13) / 당일 테스트 평균(— , 숫자 점수 입력 0명·100점 기준) / 과제 A+·A(0명) / 출결 확인 필요(9명).

좌측 명단 그리드 컬럼

컬럼 입력 방식 의미
No / 학생 정보 이름 + 소속 반 필터 탭: 전체 / 출석 / 지각·결석·조퇴, 이름순 정렬
출결 상태 4버튼 토글 + 사유 텍스트 화면①과 동일 데이터
이전 과제 재검사 "직전 B · 09/18" 표시 + [합격/불합격] 직전 수업 과제 피드백이 B 이하이면 재검사 대상 → 합/불 기록
과제피드백 A+ / A / B / C / D / F 6단계 당일 과제 등급
테스트 숫자 입력 + 컬럼 헤더에 테스트명 입력 + [저장] 당일 테스트 점수(반 단위 테스트명 1개)

우측 상세 패널 (학생 선택 시)

  • 학생 헤더: 이름, 반, [문자 복사] [이미지 복사]
  • 탭: 오늘 진도 & 코멘트 / 학습 히스토리 / 문자 미리보기
  • 당일 성취도 요약: 당일 테스트(점수 또는 서술형 결과), 과제피드백 등급
  • 오늘 수업 진도: 1~4교시 textarea (반 단위 공통)
  • 오늘의 과제: textarea (교재·범위·제출일)
  • 수업 영상 링크
  • "홍성윤T의 첨언": 반 전체 학생에게 공통 전달할 코멘트

관찰 포인트: 진도/과제/영상/첨언은 반 단위(수업일 단위) 데이터, 출결/재검사/피드백/점수는 학생 단위 데이터. 상단 안내문 "출결·과제·테스트는 표 아래 저장 · 재검사는 선택 즉시 별도 저장 · 진도와 코멘트는 메모 저장" → 저장 단위가 세 가지로 나뉨.

1.3 화면 ③ 알림문자 미리보기 (002145485.png)

화면②의 "문자 미리보기" 탭 내용으로 추정.

  • 탭: 문자 보기 / 리포트 보기(카드형 이미지) + [디자인 변경]
  • 메시지 본문 = 템플릿에 당일 데이터 자동 병합:
  • 제목(**{학생명} 학습피드백**), 인사말(학원명·강사명), 날짜
  • ■ 출결 / ■ 수업진도(교시별) / ■ 과제피드백(등급 + 서술 코멘트) / ■ 테스트(시험명, 학생점수, 반평균) / ■ 오늘의 과제 / ■ 수업 영상 링크
  • 수신 대상: 학생 / 학부모 체크박스(복수 선택)
  • 액션: 문자 복사 / 이미지 복사 / 리포트 이미지 저장 / 문자 발송

관찰 포인트: 과제피드백 등급별 서술 문구("숙제는 대부분 완료했으나 …")가 등급에 매핑된 정형 문구로 보임 → 등급→문구 템플릿 테이블 필요. 리포트 이미지 = HTML 카드를 이미지로 렌더링(html-to-image 계열).

1.4 화면 ④ 시험지 · 오답 분석 (002149983.png)

"ASSESSMENT & DIAGNOSTIC REPORT". 상단 액션: 분석지 인쇄 / 시험 등록·수정 / 엑셀 다운로드.

영역 내용
필터 날짜, 반(고3 윤A · 화6/토10 · 8명), 저장된 시험 선택(2027학년도 강대모의고사K 9회 수학영역)
난이도 분류 기준 하/중/상/최상 (접이식 설명)
최근 등록한 시험지 카드 리스트 — 파일명(.hwp), 반, 날짜, "분석 완료" 상태
시험지 등록 .hwp 업로드 → "분석 초안" 생성 → 문항 수·유형·난이도 확인 후 확정
OMR 스캔 PDF 자동 채점 연결 시험(30문항·100점 만점) 지정 → 학생 여러 명의 OMR을 PDF 1개(≤20MB/30쪽)로 업로드 → 판독 → 원본·학생·답안 확인 → 성적·정답률 반영. 안내문: "현재 ChatGPT 계정의 Codex 사용량을 사용하며 OMR 이미지가 OpenAI로 전송됩니다"
시험 KPI 응시 현황(8/8) / 반 평균 성적(63.6, 최고 80·최저 52) / 반 평균 정답률(68.3%) / 집중 해설 문항(9문항, 정답률 40% 미만)
탭 시험지 분석지 / 문항별 정오답 / 오답 유형 통계
난이도 분석표 카드형 이미지(하 13·중 9·상 6·최상 2) + [이미지 저장], "AI 추정 난이도 · 실제 정답률과 별개"
시험지 문항 분석 표 번호 / 단원 / 세부 유형("공통 객관식 10번 — 사차함수의 음의 실근 개수") / 난이도 / 판단 근거(풀이 요지). 일부 문항에 "확인 필요" 배지 + 사용자 선택값(배점 4점) 표시

관찰 포인트: 이 화면은 LLM 의존도가 가장 높은 모듈(시험지 문항 분류·난이도 추정·OMR 판독). 참조 프로그램은 OpenAI를 쓰지만, 우리는 로컬 LLM 연결이 가능한 구조로 추상화해야 함.

2. 도메인 모델 (초안)

Campus ─┬─ User(강사/원장, 로그인 계정)
        ├─ Class ──── ClassSchedule(요일·시간)
        │     └─ Enrollment ── Student ── Guardian(학부모 연락처)
        │
        ├─ ClassSession (반 × 수업일)           ← 반 단위 기록
        │     ├─ progress[1..4교시], homework, videoLink, teacherNote
        │     ├─ dailyTest { name, maxScore }
        │     └─ StudentDailyRecord (× 학생)   ← 학생 단위 기록
        │           ├─ attendance {status: 미확인|출석|지각|결석|조퇴, reason}
        │           ├─ homeworkGrade {A+|A|B|C|D|F}
        │           ├─ recheck {target:boolean, result: 합격|불합격}
        │           └─ testScore (number | text)
        │
        ├─ Exam (시험지)
        │     ├─ sourceFile(.hwp/.pdf), questionCount, maxScore, status(초안|확정)
        │     ├─ ExamQuestion[] {no, unit, subType, difficulty, rationale, points, needsReview}
        │     └─ ExamAttempt (× 학생) {answers[], score, source: OMR|manual}
        │
        ├─ ConsultLog (학생 상담일지)
        ├─ MessageTemplate / GradeComment(등급→문구)
        ├─ MessageLog {recipient, channel: SMS|LMS|MMS|알림톡, status, body, cost}
        └─ IntegrationSetting {aligo apiKey, senderNo, kakao channel, llm endpoint}

핵심 규칙 - 재검사 대상 판정: 직전 세션 homeworkGrade가 B 이하(기준값 설정 가능)이면 다음 세션에서 recheck.target = true. - 대시보드 KPI는 모두 위 테이블의 집계 뷰(주간 과제 완수율, 주간 테스트 평균 등) — 별도 저장 불필요. - 문자 본문은 ClassSession + StudentDailyRecord + GradeComment 병합 결과로 렌더 시점에 생성, 발송 시 MessageLog에 스냅샷 저장.

3. 기능 모듈 및 우선순위

# 모듈 포함 기능 우선순위 LLM 필요
M0 인증·기본 로컬 로그인(단일 계정 → 추후 다계정/역할), 캠퍼스, 설정 P0 —
M1 학생/반 관리 학생·학부모·반·수강 등록, 요일/시간, 재원 상태 P0 —
M2 일일 수업 입력 출결, 진도(교시별), 과제, 과제피드백, 재검사, 당일 테스트, 영상링크, 첨언 P0 —
M3 대시보드 KPI 카드, 반별 출결 체크, 지난 수업 요약 P1 —
M4 메시지 템플릿 병합 미리보기, 텍스트/이미지 복사, 리포트 이미지 저장, 알리고 SMS/LMS 발송, 발송 로그, 잔여량 조회 P1 —
M5 성적 통계 학생·반 시계열, 분포, 기간 비교, 엑셀 내보내기 P2 —
M6 시험지 분석 시험 등록, 문항 메타(단원·유형·난이도) 초안 생성, 확인·수정, 난이도 분석표 이미지 P2 ○
M7 OMR 채점 PDF 업로드 → 페이지 분할 → 판독 → 학생 매칭 → 검수 → 성적 반영, 문항별 정오답·오답 유형 통계 P3 ○ (Vision)
M8 카카오 알림톡 채널 연동, 승인 템플릿 관리, 발송 P3 —
M9 상담일지 학생별 상담 기록 CRUD P2 —

MVP(로컬 단독 사용) = M0 + M1 + M2 + M3 + M4(복사/이미지까지, 실제 발송은 옵션).

4. 아키텍처 방향

4.1 "로컬 우선 → 웹 전환" 전략

처음부터 웹 앱 형태로 만들되 localhost에서 띄우는 방식이 가장 전환 비용이 낮다. 데스크톱 전용 프레임워크(Electron/Tauri)를 쓰면 나중에 웹으로 갈 때 재작업이 생긴다.

단계 실행 형태 DB 인증 파일 저장
Phase A (로컬) docker compose up (api + web + postgres) → http://localhost:포트, 이후 단일 실행파일/설치 패키지 PostgreSQL (Docker 컨테이너) 로컬 계정 1개, 세션 쿠키 로컬 폴더
Phase B (웹) 컨테이너 배포(Kubernetes) PostgreSQL 다계정·역할(원장/강사), 캠퍼스 스코프 오브젝트 스토리지

DB는 처음부터 PostgreSQL 단일로 고정(SQLite 미고려, D3 확정). 전환을 쉽게 하기 위한 조건: 파일 저장을 스토리지 인터페이스로 추상화, 설정은 환경변수, 마이그레이션은 Alembic으로 처음부터 관리.

4.2 구성 요소

[React+Vite SPA] ── REST/JSON ── [FastAPI] ── [PostgreSQL]
                                     ├── [Storage] (시험지 파일, OMR PDF, 리포트 이미지)
                                     ├── [Document Ingest] (hwp/hwpx/pdf/image → 텍스트+수식+페이지 이미지)
                                     ├── [OMR Engine] (OpenCV 기반 판독, 선택적으로 학습 모델 교체)
                                     ├── [LLM Adapter] (OpenAI 호환 API — 로컬 LLM 우선)
                                     └── [Messaging Adapter] (알리고: SMS/LMS/MMS + 카카오 알림톡/친구톡)
  • 백엔드는 FastAPI(Python 3.12) + SQLAlchemy 2.0(async) + Alembic. 문서 파싱·OMR·모델 추론이 모두 Python 생태계라 단일 언어로 통합 가능(D2 확정).
  • LLM Adapter는 OpenAI 호환 chat/completions 인터페이스로 고정 → 로컬 LLM(vLLM/Ollama 등)과 외부 API를 설정만으로 교체. 문항 분류·난이도·판단 근거 생성은 이 경로.
  • OMR은 LLM/VLM이 아니라 OpenCV 템플릿 기반 판독을 기본으로 하고, 판독 결과 검수 화면을 필수로 둔다. 학습된 classification/segmentation 모델은 판독기 인터페이스 뒤에서 교체 가능하게 설계(§8 D5 참조).
  • 문서 입력은 hwp·hwpx·pdf·이미지 4종 모두 수용(§8 D6 참조).

8. 결정 항목 상세 검토

8.1 D5 — "학습시킨 classification & segmentation 모델"과 로컬 LLM의 차이

구분 학습된 분류/분할 모델 로컬 LLM / VLM
정체 특정 작업 전용 비전 모델(CNN, ViT, U-Net, YOLO 등). 라벨링된 데이터로 학습 범용 언어 모델(Llama, Qwen 등). VLM은 이미지 입력도 받음
입력→출력 이미지 → 클래스 라벨 / 픽셀 마스크·바운딩박스 텍스트(+이미지) → 자유 텍스트
강점 빠름, 결정적, 정확도 높음(학습 데이터 범위 안에서), CPU로도 실행 추론·설명·분류 근거 서술 가능, 학습 데이터 불필요(zero-shot)
약점 라벨링 데이터 준비 필요(수백~수천 장), 설명 생성 불가 느리고 비용 큼, 숫자·마킹 판독은 오판 가능, 비결정적
우리 프로젝트 적합 작업 OMR 마킹 판독(마킹/비마킹 분류, 답안 영역 분할), 시험지 문항 영역 분할 문항의 단원·세부유형·난이도 추정, "판단 근거" 문장 생성, 오답 유형 코멘트

결론: 둘은 대체 관계가 아니라 담당 작업이 다르다. 화면④의 기능을 나누면 다음과 같이 배치된다.

기능 1차 구현 고도화 옵션
OMR 판독 OpenCV 템플릿 방식 — 정렬 마커로 기울기 보정 → 격자 좌표의 마킹 농도 임계값 판독. 표준 OMR 카드는 학습 없이 95%+ 가능 마킹 판독기를 학습된 분류 모델(마킹/비마킹/이중마킹)로 교체. 학습 데이터는 운영 중 검수 화면에서 교정된 결과를 축적해 확보
문항 영역 분할 PDF 텍스트 레이어 또는 hwp 구조에서 문항 번호 기준 분리 스캔 이미지용 segmentation 모델(문항 박스 검출)
문항 분류·난이도·근거 LLM (OpenAI 호환 Adapter → 로컬 LLM) 축적된 라벨로 단원·난이도 분류기를 학습해 LLM 호출 전 사전 분류(비용 절감)

설계 원칙: OmrReader, QuestionSegmenter, QuestionAnalyzer 세 인터페이스를 두고 구현체(OpenCV / 학습 모델 / LLM)를 설정으로 교체. 검수 화면의 교정 결과는 label_corrections 테이블에 저장해 향후 학습 데이터로 재사용한다.

8.2 D6 — HWP 지원 가능 여부

포맷 구조 처리 방법 가능 여부
.hwp (HWP 5.x) OLE 복합문서 + 자체 바이너리 레코드 pyhwp(hwp5txt/hwp5html)로 본문 텍스트, 표, 이미지, 수식 스크립트 추출 가능 (텍스트·구조 추출)
.hwpx OWPML — zip 안의 XML 표준 XML 파서로 직접 처리, 수식도 XML 노드 가능 (가장 쉬움)
.pdf 텍스트 레이어 유무에 따라 상이 PyMuPDF로 텍스트·좌표·페이지 이미지 추출, 텍스트 없으면 OCR 가능
이미지 (jpg/png) 스캔·촬영본 OCR(수식 포함 시 VLM 또는 수식 OCR) → 텍스트화 가능 (정확도는 화질 의존)

hwp 관련 주의점: - 수식은 한글 자체 수식 스크립트(예: {a} over {b}, sqrt{x})로 저장되어 있어 텍스트로 추출은 되지만 LaTeX가 아니다. LLM 입력용으로는 그대로 쓰거나 간단한 변환 규칙을 둔다. - 레이아웃까지 보이는 "시각 검수용 이미지"가 필요하면 hwp → PDF 변환이 필요하다. 방법은 (a) Windows에서 한컴오피스 COM 자동화(pywin32, 로컬 단계에서 가능), (b) LibreOffice + H2Orestart 확장(리눅스 컨테이너에서 가능, 복잡한 수식·표 재현율은 한컴보다 낮음). 웹 단계(K8s)에서는 (b) 또는 Windows 변환 워커를 별도로 둔다. - 배포 금지 설정·암호가 걸린 hwp는 파싱이 안 된다. 업로드 시 오류로 안내. - 수식이 이미지(그림 개체)로 삽입된 시험지는 텍스트 추출이 불가능해 이미지 경로(OCR/VLM)로 폴백한다.

결론: 4종 모두 지원 가능. 파이프라인은 DocumentIngest(file) → {pages[], blocks[](text|equation|image|table), page_images[]} 공통 구조로 정규화한 뒤 문항 분할·분석으로 넘긴다.

항목 필요 사항

8.4 D10 — 추론 하드웨어 전략

LLM이 필요한 작업은 시험지 등록 시 문항 분석 1회(시험지당 5만~10만 토큰, 주 수 회)뿐이며 실시간성이 필요 없는 배치 작업이다. OMR 판독(OpenCV)·통계·메시지는 GPU가 필요 없다.

선택지 초기 비용 운영 비용 품질 판단
A. CPU + 7~14B 로컬 모델 0 전기료 낮음~중간 (고3 수학 문항 분류·근거 서술에 부족) 외부 전송 불가 시 폴백
B. 소비자 GPU (RTX 3090 24GB 중고 등) 약 60~100만원 전기료 중간~높음 단일 학원용으로 과투자
C. Mac mini 통합메모리 48~64GB 약 200~300만원 낮음 중간~높음 단일 학원용으로 과투자
D. 외부 LLM API 종량제 0 시험지당 수십~수백 원 높음 Phase A 권장
E. 웹 전환 후 중앙 GPU 1대 공유 서버 1대 학원 수로 분산 높음 Phase B 권장

개인정보 경계: 시험지 문항에는 학생 정보가 없으므로 외부 API로 보내도 되고, 학생 이름·수험번호가 있는 OMR은 로컬 OpenCV로만 처리한다.

8.5 D11 — OMR 답안지 양식 분석 및 판독 설계

입력 양식: 2027학년도 대학수학능력시험 수학영역 답안지(가로형, 분홍색 인쇄). 클라이언트가 이 양식으로 고정함.

양식 구조

영역 위치 구성 판독 방식
타이밍 마크 상·하·좌·우 가장자리의 검은 사각형 열 인쇄 위치 고정 기울기·원근 보정 및 좌표 정합의 기준점
성명 좌측 상단 손글씨 판독 대상 아님 (수험번호로 학생 매칭, 실패 시 검수 화면에서 수동 선택)
수험번호 좌측 8자리 × 숫자 0~9 마킹 학원이 학생별 8자리 번호를 부여해 학생 매칭 키로 사용
문형 좌측 중앙 홀수형 / 짝수형 정답표 변형 선택 (시험당 정답표 2벌 지원)
공통과목 객관식 중앙 상단 1~10, 11~15 (15문항 × 5지) 단일 마킹, 복수 마킹·무마킹 플래그
단답형 16~22번 중앙 하단 및 우측 상단 문항당 백(1~9)·십(0~9)·일(0~9) 3열 열별 단일 마킹 → 정수 조합, 백의 자리 무마킹 허용
선택과목 객관식 23~28 우측 하단 6문항 × 5지 단일 마킹
단답형 29~30번 우측 백·십·일 3열 단답형과 동일
결시자 확인·필적 확인·감독관 확인 좌측 — 판독 제외

합계 30문항 = 객관식 21 + 단답형 9. 배점은 시험 등록 시 문항별 입력(수능 표준 2·3·4점).

판독 파이프라인 (CPU, OpenCV)

단계 처리 비고
1. 페이지 분리 PDF → 페이지별 이미지(300 DPI 권장) 촬영본(jpg)도 동일 경로
2. 색 분리(drop-out) RGB의 R 채널만 사용 → 분홍 인쇄는 흰색에 가깝게 사라지고 검은 마킹만 남음 스캐너의 컬러 드롭아웃과 같은 원리, 별도 학습 불필요
3. 정합 타이밍 마크·모서리 마크 검출 → 호모그래피로 기준 템플릿 좌표계에 정렬 기울기·원근·크기 차이 흡수
4. 버블 판독 템플릿 JSON에 정의된 각 버블 중심·반경의 평균 농도 계산 → 행 내 상대 비교 + 절대 임계값으로 마킹 판정 판정값·신뢰도 저장
5. 값 조합 객관식 1~5, 단답형 3열 → 정수, 수험번호 8자리, 문형 복수 마킹·무마킹·저신뢰는 플래그
6. 학생 매칭 수험번호 ↔ 학생 테이블 미매칭 시 검수 화면에서 수동 지정
7. 검수 원본 크롭과 판독 결과를 나란히 표시, 플래그 문항 우선 표시, 교정값은 label_corrections에 저장 향후 학습 모델 데이터
8. 채점·반영 문형별 정답표와 대조 → ExamAttempt 저장, 문항별 정답률 갱신 —

원본 PDF 확인 결과 (assets/omr/omr-template-ksat2027-math.pdf, A4 가로 297×210mm, 내장 이미지 1754×1240 ≈ 150 DPI 스캔본 + OCR 텍스트 레이어)

  • 수험번호 8자리는 자리마다 마킹 가능한 숫자 범위가 다르다: 1열 1~9, 2열 0~9, 3열 0~5, 4열 0~9, 5열 0~9, 6열 0~9, 7열 0~2, 8열 0~9 (총 68버블). 학원이 학생별 수험번호를 부여할 때 이 범위를 지켜야 하며, Student.omr_number 저장 시 검증한다.
  • 4 모서리 마크(정규화 좌표 x 0.0724/0.9276, y 0.0200/0.9690)가 대칭으로 존재해 호모그래피 기준점으로 충분하다. 상단 타이밍 마크 40개는 보조 검증용.
  • 버블 크기 약 2.2×4.6mm(세로 타원). 인쇄색은 R 채널에서 거의 사라짐을 확인.

템플릿 및 프로토타입 산출물 (prototype/omr/)

파일 내용
ksat-2027-math.json 버블 437개(객관식 105 + 단답형 261 + 수험번호 68 + 문형 2 + 결시 1)와 모서리·타이밍 마크의 정규화 좌표. PDF에서 자동 추출, 전 필드 행·열 수 검증 완료
omr_reader.py 판독 참조 구현 — 모서리 마크 검출 → 호모그래피 정합(3508×2480 캔버스) → R 채널 드롭아웃 → 버블 농도 → 필드별 판정(정상/무마킹/복수마킹/저신뢰)
test_omr.py 합성 테스트 — 난수 답안·수험번호를 마킹한 뒤 회전 3°·축소 0.6·원근 왜곡·회색 배경을 적용하고 판독. 30문항·수험번호·문형 전부 일치, 의도된 복수마킹(3번)·무마킹(22번) 플래그 정상
template.py, detect.py 템플릿 JSON 생성 스크립트(양식 변경 시 재실행)

남은 검증: 실제 학생 마킹 스캔본(사인펜 농도, 지우개 자국, 스캐너별 밝기 차이)으로 임계값(abs_th=70, rel=0.5)을 보정해야 한다. 합성 테스트는 판독 로직과 정합이 맞는지만 보장한다.
