## 요약

- 결정: Phase A부터 다계정·역할(`원장`·`강사`)과 캠퍼스 스코프 권한을 구현하고, 스코프 강제를 리포지토리 기반 클래스와 라우터 의존성 두 지점에 고정한다.
- 핵심 이유: 단일 계정으로 먼저 만들면 모든 조회·변경 API에 스코프 인자를 나중에 끼워 넣어야 해 전면 재작업이 된다.
- 주요 단점: 로컬 단독 사용 시점에는 필요 없는 구현과 테스트 비용이 앞당겨진다.

## 배경

참조 프로그램 화면에는 캠퍼스 전환 드롭다운과 로그인 사용자 표시(강사)가 있고, 대시보드는 원장 모드 배지를 노출한다. Phase A는 로컬 단독 사용이라 계정 1개로도 동작하지만, Phase B는 다중 학원·다중 강사를 전제한다.

## 영향을 받는 요구사항과 제약

- [FR-03 캠퍼스 관리와 스코프](../../requirements.md#fr-03-상세): 모든 조회·변경이 스코프로 제한되어야 한다.
- [NFR-07 권한 적용](../../requirements.md#비기능-요구사항): 검사 누락을 테스트로 탐지할 수 있어야 한다.
- 사용자 결정: Phase A부터 다계정·역할을 구현한다.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| A. Phase A부터 다계정·역할·스코프 (선택) | 재작업 없음, 권한 테스트를 처음부터 축적 | 초기 구현·테스트 비용 | — |
| B. 단일 계정 후 Phase B에서 도입 | 초기 구현 최소 | 전 API 시그니처·쿼리 재작업, 권한 누락 위험 | 높음 |
| C. 데이터에 `campus_id`만 두고 검사 없음 | 스키마 전환 비용 없음 | 스코프 강제가 없어 사실상 재작업과 동일 | 높음 |

## 결정

1. `app_user`(역할 `director`·`teacher`)와 `app_user_campus`로 계정·접근 캠퍼스를 관리한다.
2. 인증은 서버 세션 + `HttpOnly`·`SameSite=Lax` 쿠키, 비밀번호는 Argon2id 해시로 저장한다.
3. 라우터는 `CurrentScope(user, campus_id, role)` 의존성을 통해서만 서비스를 호출하고, 리포지토리 기반 클래스가 `campus_id` 필터를 요구한다.
4. 강사는 담당 반과 그 반 소속 학생으로 접근을 제한하며, 사용자 관리와 연동 설정은 원장 전용이다.
5. 권한 거부는 403으로 통일하고 자원 존재 여부를 응답 본문에 노출하지 않으며 감사 로그에 남긴다.
6. 초기 원장 계정은 최초 기동 시 환경변수로 1회 생성한다.

## 이유

1. 스코프 인자는 모든 쿼리의 시그니처에 영향을 주므로 나중에 도입하면 사실상 전 API 재작성이다.
2. 강제 지점을 두 곳(라우터 의존성·리포지토리 기반 클래스)으로 고정하면 누락을 엔드포인트 목록 기반 테스트로 탐지할 수 있다([RISK-08](../../design.md#위험)).
3. 참조 프로그램의 화면 구성이 이미 다계정·다캠퍼스를 전제한다.

## 결과와 감수할 단점

- 로컬 단독 사용자는 계정 1개만 쓰면서도 로그인 절차를 거친다. 초기 계정 자동 생성으로 마찰을 줄인다.
- 권한 테스트 매트릭스 유지 비용이 생긴다. 엔드포인트 목록에서 테스트를 생성해 완화한다.
