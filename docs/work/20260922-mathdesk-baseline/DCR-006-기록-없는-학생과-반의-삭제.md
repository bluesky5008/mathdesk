- 사용자 재승인 결과: 대기

## 변경 사유와 증거

- **계기:** 사용자가 "학생과 반 목록을 삭제하는 기능이 보이지 않는다"고 보고했다(2026-09-24).
- **기준선의 배제 이유(유효):** 출결·과제·점수·발송·시험·상담 기록이 학생과 반을 참조한다. 물리 삭제는 이 과거 기록을 깨뜨린다. 그래서 FR-05는 퇴원, FR-07은 활성 여부만 요구했다(2026-09-23 검토에서 재확인).
- **배제로 생기는 실제 공백:** 운영 이관 뒤 클라이언트는 8개 반·학생 160명을 **손으로 입력**한다(작업 기록 사이클 3 계획). 이름을 잘못 쓰거나 같은 학생을 두 번 넣는 입력 실수는 기록이 생기기 전에 발견된다. 지금은 이런 항목도 퇴원·비활성으로 남길 수밖에 없어, 목록과 수험번호(캠퍼스 내 유일)를 영구히 점유한다.
- **보류한 구현:** 없음. 삭제 코드는 작성하지 않았다. 목록 행의 퇴원·비활성 버튼(①)은 기존 동작을 바꾸지 않아 경량 경로로 반영했다(커밋 `b4a410d`).

## 기존 설계와 제안 설계

### 기존 (기준선 `v6`)

- FR-05: 학생 등록·수정·검색·퇴원. 퇴원 학생은 기본 목록에서 빠지고 과거 기록은 보존된다. 삭제 없음.
- FR-07: 반 등록·수정, 활성 여부. 삭제 없음.
- REST: `DELETE`는 `/classes/{id}/enrollments/{id}`(오등록 배정 취소)뿐.

### 제안 (기준선 `v7`)

**삭제할 수 있는 조건 — "활동 기록이 하나도 없다"**

| 대상 | 활동 기록(하나라도 있으면 삭제 거부) | 함께 지워지는 것 |
|---|---|---|
| 학생 | 일일 기록, 시험 응시, 매칭된 답안지, 발송 내역, 상담 기록 | 보호자, 반 배정 |
| 반 | 연결된 시험, 그 반 수업에 입력된 내용(일일 기록·진도·과제·영상 링크·강사 메모·테스트명·출결 확정) | 시간표, 반 배정, 입력 내용이 없는 빈 수업 세션 |

**동작**

1. 원장만 삭제할 수 있다(강사는 403). 다른 캠퍼스 자원은 기존 스코프 규칙대로 403.
2. 삭제는 한 트랜잭션에서 **조건 검사와 삭제를 함께** 한다. 검사와 삭제 사이에 기록이 생기면 삭제하지 않는다(대상 행 잠금).
3. 조건을 만족하면 삭제하고 `204`. 만족하지 않으면 **아무것도 지우지 않고** `409`와 사유를 돌려준다. 예: "출결·과제 기록 12건, 발송 내역 3건이 있어 삭제할 수 없습니다. 퇴원 처리해 주세요."
4. 삭제마다 감사 로그를 남긴다(`student.delete`·`class.delete`, 대상 ID, 함께 지운 건수). 개인정보인 이름은 감사 로그에 쓰지 않는다.
5. 삭제한 학생의 수험번호는 다시 쓸 수 있게 된다.

**화면:** 학생·반 **[수정] 대화상자 아래쪽**에 [삭제]를 둔다. 누르면 확인창("기록이 없는 경우에만 삭제됩니다. 되돌릴 수 없습니다.")을 거쳐 요청하고, 거부되면 사유를 대화상자에 보여 준다. 목록 행에는 두지 않는다 — 행의 [퇴원]·[비활성]과 나란히 두면 잘못 누를 위험이 크고, 삭제는 드문 조작이다.

## 대안 분석

| 대안 | 장점 | 단점·위험 | 판단 |
|---|---|---|---|
| A. 기록 없을 때만 실제 삭제 (선택) | 입력 실수를 깨끗이 지운다. 과거 기록은 구조적으로 깨질 수 없다 | "기록"의 정의를 테이블이 늘 때마다 함께 넓혀야 한다(새 참조 테이블 추가 시 누락 위험) | **채택** — 누락은 테스트로 막는다(아래 검증) |
| B. 소프트 삭제(`deleted_at`으로 숨김) | 되돌릴 수 있다 | 퇴원·비활성과 사실상 같은 기능이 하나 더 생긴다. 숨긴 학생이 수험번호를 계속 점유한다. 모든 조회에 숨김 조건을 넣어야 한다 | 기각 — 이미 있는 퇴원·비활성과 겹친다 |
| C. 기록째 연쇄 삭제 | 구현이 가장 단순하다 | 출결·성적·발송 이력이 사라져 통계와 과거 반 재현(FR-08)이 깨진다. 되돌릴 수 없다 | 기각 — 기준선이 배제한 이유 그대로 |

**ADR을 만들지 않는 이유:** 기술 선택이 아니라 요구사항(무엇을 지울 수 있는가)의 조정이며, 저장 방식·구조를 바꾸지 않는다.

## 마이그레이션과 롤백

- **마이그레이션:** 없음.
- **롤백:** 두 `DELETE` 경로와 [삭제] 버튼을 제거하면 기준선 `v6` 동작으로 돌아간다. 이미 삭제된 데이터는 되돌리지 않는다(백업 복원으로만 가능).

## 검증 방법

- **AC-36:** API 통합 테스트 — 기록 없는 학생 삭제 → 보호자·배정까지 사라짐, 수험번호 재사용 가능. 활동 기록 종류마다 하나씩 만든 학생의 삭제 → 409, 모든 행 불변. 반도 같은 방식(빈 수업 세션은 삭제를 막지 않고, 입력 내용이 있는 세션·연결된 시험은 막음).
- **기록 정의 누락 방지:** `student`·`class`를 외래키로 참조하는 테이블 목록을 모델에서 읽어, 삭제 규칙이 모두 다루는지(활동 기록 또는 함께 삭제로 분류됐는지) 확인하는 테스트를 둔다. 새 참조 테이블이 생기면 이 테스트가 실패한다.
- 강사 403, 다른 캠퍼스 403, 감사 로그 기록.
- 웹: 수정 대화상자의 [삭제] → 확인 → 목록에서 사라짐, 거부 사유 표시.

## 남은 위험과 미해결 사항

- 삭제는 되돌릴 수 없다. 운영에서는 자동 백업(TASK-57)이 갖춰진 뒤 쓰는 것이 안전하다.
- 기록이 있는 학생의 "잘못 입력된 기록"(예: 다른 학생에게 잘못 입력한 출결)은 이 DCR로 해결되지 않는다. 그 기록을 고치는 기존 수정 경로를 쓴다.
