- 변경 분류: **설계 변경**(데이터 모델·API 계약) + 요구사항 명확화(FR-07의 "시간"을 "시작 시각"으로) + 인수 조건 신설(AC-37).

- 사용자 결정(2026-09-24): "수업 시간이 동일하므로 시작 시각만 알면 종료는 자동으로 안다" → 방안 A(종료 시각 선택 항목)를 골랐다.

## 변경 사유와 증거

- **계기:** 사용자가 휴대폰 캡처로 반 목록의 "시간표 없음"이 무슨 뜻인지 물었다(2026-09-24).
- **확인한 사실:**
  1. 화면에는 시간표를 입력할 곳이 없다. [반 등록]은 시간표를 항상 빈 상태로 만들고(`ClassesPage.tsx` `createClass(... schedules: [])`), [수정] 대화상자는 시간표를 읽기 전용으로 보여 준다. API(`POST`·`PATCH /classes`)는 시간표를 받을 수 있다. 시간표가 있는 반은 시드 데이터뿐이다.
  2. **FR-07은 "요일·시간 시간표를 등록·수정"을 요구한다.** 반 수정 작업(TASK-51)의 완료 조건이 시간표 편집을 검사하지 않아 빠진 채 완료되었다. 작업 기록에는 \"기능 공백 — 후속 후보\"로 잘못 분류되어 있었다(실제로는 승인된 요구사항 미구현).
  3. `class_schedule.end_time`은 필수(NOT NULL)이고 API도 필수로 받지만, **시스템 어디에서도 종료 시각을 쓰지 않는다**(화면 표시 \"화 18:00~22:00\"뿐). 일일 입력·대시보드·통계·발송은 시간표를 보지 않는다.
- **사용자 결정:** 수업 시간이 반마다 같아서 종료 시각은 필요 없다. 시작 시각만 입력·표시한다.
- **보류한 구현:** 없음.

## 기존 설계와 제안 설계

### 기존 (기준선 `v7`)

- FR-07: 반명, 학년, 담당 강사, **요일·시간** 시간표, 활성 여부를 등록·수정.
- 데이터 모델 `class_schedule`: `id`, `class_id`, `weekday`, `start_time`, `end_time`(필수).
- REST: `POST /classes`·`PATCH /classes/{id}`의 `schedules[]` 항목은 `weekday`·`start_time`·`end_time` 모두 필수.
- 화면: 시간표 입력 없음(미구현), 목록은 \"화 18:00~22:00\" 형식 또는 \"시간표 없음\".

### 제안 (기준선 `v8`)

- **FR-07 명확화:** 시간표는 **요일과 시작 시각**으로 등록·수정한다. 수업 길이는 반마다 같아 종료 시각은 입력하지 않는다.
- **데이터 모델:** `class_schedule.end_time`을 **선택(NULL 허용)**으로 바꾼다. 기존 값은 그대로 둔다.
- **REST:** `schedules[]`의 `end_time`을 선택 항목으로 바꾼다(보내지 않으면 비워 저장). 같은 요일·시작 시각이 두 번 들어오면 `422`. 기존 클라이언트가 `end_time`을 보내도 그대로 받는다(하위 호환).
- **화면:** [반 등록]과 [수정] 대화상자에 시간표 편집을 둔다 — 줄마다 요일 선택 + 시작 시각, [시간 추가]·[삭제]. 목록·대화상자는 **\"화 18:00 · 토 10:00\"**처럼 시작 시각만 보여 준다(종료 시각이 저장돼 있어도 표시하지 않는다). 시간표가 없으면 기존처럼 \"시간표 없음\".
- **AC-37 신설:** 반 등록·수정에서 요일과 시작 시각으로 시간표를 입력·수정·삭제할 수 있고, 목록에 \"요일 시작 시각\"으로 표시된다. 같은 요일·시작 시각을 두 번 넣으면 저장되지 않는다.

## 변경 항목

| 항목 | 기존 | 변경 | 이유 |
|---|---|---|---|
| FR-07 | 요일·시간 시간표 | 요일·**시작 시각** 시간표(종료 시각 입력 없음) | 사용자 결정 — 수업 길이가 같다 |
| AC-37 | 없음 | **신설** — 위 제안 | 미구현이던 시간표 입력의 검증 |
| 데이터 모델 `class_schedule.end_time` | 필수 | 선택(NULL 허용) | 쓰이지 않는 값을 강제하지 않는다 |
| REST `schedules[].end_time` | 필수 | 선택, 중복(요일+시작) 422 | 위와 같음, 입력 실수 방지 |
| 화면 | 입력 없음, 범위 표시 | 등록·수정에서 편집, 시작 시각만 표시 | FR-07 구현 |

## 대안 분석

| 대안 | 장점 | 단점·위험 | 판단 |
|---|---|---|---|
| A. 종료 시각 선택 항목 (선택) | 의미 없는 값을 남기지 않는다. 기존 데이터를 지우지 않아 되돌리기 쉽다 | 스키마 변경(마이그레이션 1개) | **채택**(사용자 선택) |
| B. 수업 시간 설정으로 종료 시각 자동 계산 | 스키마 그대로. 나중에 \"수업 중\" 표시 등에 종료 시각을 쓸 수 있다 | 수업 시간 설정이 하나 늘고 그 값을 정해야 한다 | 기각 — 종료 시각을 쓸 곳이 없다 |
| C. 종료 시각에 시작 시각을 저장 | 변경이 가장 적다 | 저장된 값이 의미를 잃어 나중에 오해를 만든다 | 기각 |

**ADR을 만들지 않는 이유:** 값 하나를 선택 항목으로 바꾸는 국소 변경이며 되돌리기 쉽다.

## 마이그레이션과 롤백

- **마이그레이션:** `ALTER COLUMN end_time DROP NOT NULL`. 데이터 변경 없음.
- **롤백:** 비어 있는 `end_time`을 `start_time`으로 채운 뒤 NOT NULL을 되돌린다(downgrade에 포함). 화면은 이전 커밋으로 되돌린다.

## 검증 방법

- **AC-37:** API — `end_time` 없이 시간표 저장·재조회(`end_time`은 null), 기존처럼 `end_time`을 보내도 저장, 중복 422. 웹 — 등록 폼에서 요일·시작 시각 두 줄 입력 → 요청 본문 확인, 수정 대화상자에서 줄 추가·삭제, 목록 표시 \"화 18:00 · 토 10:00\".
- 마이그레이션 왕복(`test_migrations.py`).
- 기존 반 관련 테스트 통과(표시 문자열 단위 테스트는 새 규칙으로 기대값 변경).

## 남은 위험과 미해결 사항
