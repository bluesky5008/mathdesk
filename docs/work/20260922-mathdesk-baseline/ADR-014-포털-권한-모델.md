## 요약

- 결정: 학생·학부모를 기존 `app_user`의 새 역할(`student`·`guardian`)로 두되, 기존 스코프 의존성은 원장·강사만 통과시키고 포털은 `/api/portal` 아래의 별도 의존성·라우터로만 접근하게 한다(기본 거부). 계정과 학생의 연결은 별도 테이블(계정 1 : 학생 N)로 둔다.
- 핵심 이유: 인증(세션·잠금·비밀번호 변경 강제)은 그대로 재사용하면서, 기존 라우터가 "강사도 가능"을 기본으로 하는 구조에서 새 역할이 기존 API를 쓰게 되는 사고를 구조적으로 막는다.
- 주요 단점: 포털 조회 엔드포인트를 기존 엔드포인트와 별도로 둬야 하므로 내부 함수 재사용에 신경 써야 한다.

## 배경

[ADR-007](./ADR-007-인증-권한-모델.md)은 역할을 `director`·`teacher` 둘로 두고, 스코프 강제를 라우터 의존성(`CurrentScope`)과 리포지토리 기반 클래스 두 지점에 고정했다. 권한 분기는 `require_director()` 한 가지뿐이고 나머지 라우터는 강사도 쓸 수 있다는 전제다. [DCR-024](./DCR-024-학생-학부모-포털.md)로 학생·학부모가 로그인하게 되면서, 이들이 **본인(자녀) 데이터만** 보고 원장·강사 기능에는 전혀 닿지 못하게 하는 구조가 필요하다.

## 영향을 받는 요구사항과 제약

- FR-48·FR-49(DCR-024): 포털 계정 발급과 조회 전용 화면.
- NFR-07: 모든 API 요청이 역할·캠퍼스 검사를 통과하고 누락을 테스트로 탐지한다.
- NFR-06: 비밀번호 해시·세션·잠금은 계정 종류와 무관하게 적용한다.
- 제약: 형제를 둔 학부모는 계정 하나로 자녀 여럿을 본다(사용자 결정). 로그인 ID는 전역 유일이다.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| A. 같은 `app_user`에 역할 추가 + 기존 스코프는 원장·강사만 통과 + `/api/portal` 별도 의존성·라우터 + 연결 테이블 `app_user_student` (선택) | 로그인·세션·잠금·비밀번호 변경 강제·`ForcedPasswordChange`를 그대로 재사용. 포털 역할은 기존 API 전부에서 구조적으로 403. 포털 응답 모델을 따로 좁혀 다른 학생 정보가 섞이지 않음 | 포털 조회 엔드포인트를 따로 만들어야 함(내부 함수는 공유) | — |
| B. 별도 테이블 `portal_account`·`portal_session`과 별도 인증 | 원장·강사 계정 테이블이 전혀 바뀌지 않음 | 로그인·잠금·세션·비밀번호 변경 코드와 테스트가 두 벌이 되고 NFR-06 정책이 갈라질 위험 | 높음 |
| C. 역할만 추가하고 기존 라우터마다 역할 검사를 더함 | 엔드포인트 추가 없음 | 기본 허용이라 검사 하나만 빠져도 포털 계정이 반 전체·연락처를 봄. 기존 응답에 다른 학생 정보가 섞여 있어 좁히기 어려움 | 낮아 보이나 누락 위험이 큼 |

## 결정

1. `app_user.role`에 `student`·`guardian`을 더한다. 인증(`/auth/login`·`/auth/me`·`/auth/password`·로그아웃), 세션, 잠금, `must_change_password` 흐름은 모든 역할이 공유한다.
2. 기존 `current_scope`는 `director`·`teacher`만 통과시키고 포털 역할에는 403을 돌려준다. 포털 라우터는 `/api/portal` 접두사 아래에만 두고 `current_portal_scope`만 쓴다. 이 의존성은 포털 역할만 통과시키고 `PortalScope(user, campus_id, student_ids)`를 돌려준다.
3. 계정–학생 연결은 `app_user_student(user_id, student_id, guardian_id?)`로 둔다. 학생 계정은 학생 1명, 학부모 계정은 N명과 연결된다. `student_ids`는 재원·휴원 학생만 담는다.
4. 포털 엔드포인트는 `student_id`가 `scope.student_ids`에 없으면 403이며, 응답 모델은 다른 학생·보호자·연락처 정보를 담지 않도록 포털 전용으로 정의한다. 데이터 계산은 기존 서비스의 내부 함수를 재사용한다.
5. NFR-07의 엔드포인트 목록 테스트를 양방향으로 확장한다: 포털 역할로 포털 외 전부 403, 원장·강사로 포털 전부 403.
6. 포털 계정은 `app_user_campus`에 학생의 캠퍼스 1행을 가진다. 포털 계정의 발급·재발급·비활성·삭제는 학생 관리(DES-04)가 소유하며 설정의 계정 관리 화면은 원장·강사만 다룬다.
7. 발급 만료(발급 뒤 7일 안에 최초 비밀번호 변경이 없으면 로그인 거부)는 포털 역할에만 적용한다.

## 이유

1. 인증 정책(NFR-06)이 한 벌이면 잠금·세션·만료가 계정 종류에 따라 갈라지지 않는다.
2. 기본 거부를 의존성 수준에서 고정하면 포털 역할이 기존 API를 쓰는 사고가 "검사 누락"이 아니라 "구조상 불가"가 된다. ADR-007이 스코프를 두 지점에 고정한 것과 같은 논리다.
3. 포털 응답을 별도 모델로 좁히면 "본인 데이터만"이 응답 스키마로 보장되고 테스트로 확인할 수 있다.
4. 연결 테이블은 형제(계정 1 : 학생 N)와 보호자별 발급(어느 번호로 발급됐는지)을 자연스럽게 표현한다.

## 결과와 감수할 단점

- 포털 조회 REST가 기존 조회 REST와 따로 생긴다(7건). 계산 로직을 함수로 공유하지 않으면 두 벌이 되므로 구현 시 재사용을 강제한다.
- 역할 열거형이 늘어 `role === 'director'` 식의 분기가 있는 웹 코드는 포털 역할을 셸 진입에서 먼저 걸러야 한다.
- `audit_log.actor_id`가 포털 계정을 가리킬 수 있어 계정 삭제 시 NULL 처리가 필요하다.

## 후속 작업

- NFR-07 양방향 권한 테스트 확장.
- 삭제 외래키 테스트에 `app_user_student`·고아 포털 계정 반영.
- 클라이언트 안내문에 발급·재발급 절차와 선점 주의 추가.
