## 요약

- 결정: 프론트엔드는 React 18 + Vite + TypeScript SPA, 백엔드는 FastAPI(Python 3.12) + SQLAlchemy 2.0 async + Alembic 단일 서비스로 구성하고, Phase A는 로컬 `docker compose`로 실행한다.
- 핵심 이유: 문서 파싱·OpenCV·모델 추론이 모두 Python 생태계이므로 백엔드를 한 언어로 통합할 수 있고, 웹 앱 형태를 유지하면 Phase B 전환에 재작업이 없다.
- 주요 단점: 로컬 사용자가 Docker를 설치·기동해야 하며 순수 설치형 실행파일보다 진입 장벽이 높다.

## 배경

이 시스템은 단일 학원의 로컬 PC에서 먼저 사용하고(Phase A), 이후 여러 학원을 대상으로 하는 웹 서비스로 전환할 계획이다(Phase B). 동시에 시험지 파싱(hwp/hwpx/pdf), OMR 판독(OpenCV), 문항 분석(LLM 호출)처럼 Python 생태계에 강하게 의존하는 처리가 필요하다.

## 영향을 받는 요구사항과 제약

- [NFR-08 이식성](../../requirements.md#비기능-요구사항): Phase A와 B가 동일한 이미지·설정 방식을 사용해야 한다.
- [FR-27 시험지 업로드](../../requirements.md#fr-27-상세), [FR-33 OMR 판독](../../requirements.md#fr-33-상세): 문서 파싱과 영상 처리가 백엔드에 필요하다.
- 클라이언트 하드웨어 증설은 전제하지 않는다.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| A. React SPA + FastAPI 단일 백엔드 (선택) | 언어 통합, 웹 전환 무재작업, 테스트 용이 | 로컬 실행에 Docker 필요 | — |
| B. Electron/Tauri 데스크톱 앱 | 설치·실행이 쉬움, 오프라인 친화 | 웹 전환 시 UI·배포 구조 재작업, 파이썬 런타임 번들 복잡 | 높음 |
| C. Node 백엔드 + 별도 Python ML 서비스 | JS 단일 언어 프론트·백 | 서비스 2개 운영, IPC·배포 복잡도 증가 | 중간 |
| D. 서버 렌더링 프레임워크(Django 템플릿 등) | 초기 개발 빠름 | 일일 입력 화면의 복잡한 부분 저장·상호작용 구현이 불리 | 중간 |

## 결정

React 18 + Vite + TypeScript SPA(라우팅 React Router, 서버 상태 TanStack Query)와 FastAPI + SQLAlchemy 2.0 async + Alembic 단일 백엔드를 채택한다. Phase A 실행 형태는 `docker compose`(api + web + postgres)이며, 이후 필요 시 설치 패키지 배포를 별도 결정으로 다룬다.

## 이유

1. 문서 파싱·OpenCV·추론이 전부 Python이라 백엔드를 Python으로 두면 별도 ML 서비스 분리와 그 운영 비용이 사라진다.
2. 웹 앱 형태를 유지하면 Phase B에서 동일 코드·동일 이미지를 그대로 사용할 수 있어 전환 비용이 사실상 0이다.
3. 일일 입력 화면은 표 기반 부분 저장과 즉시 저장이 섞여 있어(FR-14) 클라이언트 상태 관리가 필요한 SPA가 적합하다.

## 결과와 감수할 단점

- 로컬 사용자는 Docker Desktop 설치와 컨테이너 기동 절차를 따라야 한다. 실행 스크립트와 안내 문서로 완화한다.
- 프론트·백 분리로 계약(REST 스키마) 관리 비용이 생긴다. Pydantic 스키마에서 타입을 생성해 완화한다.

## 후속 작업

- API 스키마에서 프론트 타입 생성 파이프라인 구성
