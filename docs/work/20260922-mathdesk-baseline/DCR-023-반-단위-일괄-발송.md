## 요약

- 변경 분류: **요구사항 변경 + 공개 인터페이스 추가** — 알림 문자 화면에서 **반·수업일을 고르면 그날 배정된 학생 전원에게 한 번에** 문자(또는 알림톡)를 보낼 수 있게 한다(FR-47 신설). 학생마다 본문은 기존 규칙대로 개별 생성(FR-18)하고, 발송은 백그라운드 작업으로 돌리며, 결과를 학생별로 보이고 실패한 학생만 다시 보낼 수 있다. REST 1건(일괄 발송 등록)을 더하고 기존 1명 발송은 그대로 둔다. 데이터 모델은 `message_log.session_id`(비어 있을 수 있는 수업 참조) 열 하나를 더한다(구현 중 보정, 사용자 승인 2026-10-11 — 아래 변경 이력).
- 변경 요지: ① [반 전체 발송] 버튼 → 확인 창(대상 N명, 연락처 없는 학생·오늘 이미 보낸 학생 제외 목록, 학생/학부모 선택, 알림톡 템플릿) → 등록 ② 서버가 학생별로 본문을 만들어 순서대로 발송하고 로그를 남긴다 ③ 화면은 진행률을 폴링하고 끝나면 학생별 결과 표와 [실패만 다시 보내기]를 보인다.
- 사용자 결정 필요: 없음(세부는 Claude 추천안. 수정 요청으로 바꿀 수 있다).
- 사용자 재승인 결과: **승인 (2026-10-11)** — 기준선 `v23` → `v24` 발행

## 변경 사유와 증거

- **계기:** 2026-10-11 문자 발송 연결 검토에서 "학생 1명 단위 발송만 있어 160명이면 160번 보내야 한다"를 빈틈으로 보고했고, 사용자가 "반 단위 일괄 발송은 필요하다"고 확인했다.
- **확인한 사실:**
  1. `POST /messages/send`는 `{session_id, student_id, recipients[], template_code?}`로 **학생 1명**만 받는다. 화면(`MessagesPage`)도 반·날짜·학생을 고른 뒤 [보내기]다.
  2. 본문은 `render_daily_message(context)`로 학생마다 다르게 만들어진다(반 공통 + 학생 개별). 알림톡은 `render_alimtalk`. 수신자는 `_recipients_for(student, kinds)`가 학생·학부모 번호를 모은다.
  3. 어댑터는 수신자 1명마다 알리고에 1회 요청한다. 160명 × 최대 2명 = 최대 320회, 요청당 수백 ms면 **수 분**이라 HTTP 요청 하나 안에서 끝낼 수 없다.
  4. 오래 걸리는 작업은 `TaskRunner`(DES-18, `background_task` 테이블, `GET /tasks/{id}` 폴링, 재시작 시 `queued` 재개)가 이미 있고 시험지 분석이 쓴다.
  5. 발송 로그는 수신자 단위이며 `student_id`·`requested_at`을 가진다. 같은 수업일에 이미 보냈는지는 로그로 알 수 있다.
  6. 실패 건 재시도 버튼은 설계 흐름 5번에 있으나 미구현이다.
- **보류한 구현:** 없음.

## 제안

### 요구사항

- **FR-47(신설) 반 단위 일괄 발송:** 알림 문자 화면에서 반·수업일을 고르고 [반 전체 발송]을 누르면, 그 수업일에 그 반에 배정된 학생 전원이 대상이 된다. 수신 대상(학생/학부모)과 알림톡 템플릿은 전체에 공통으로 고르고, 본문은 학생마다 FR-18대로 따로 만든다. 발송 전에 **확인 창**이 대상 수, 보낼 연락처가 없어 빠지는 학생, 같은 수업일에 이미 보낸 학생(기본 제외, 체크로 포함)을 보인다. 발송은 백그라운드에서 순서대로 진행되고 화면이 진행률을 보이며, 끝나면 학생별 결과(수신자·채널·상태·실패 사유)와 [실패만 다시 보내기]가 보인다. 발송 로그(FR-23)는 기존처럼 수신자 단위로 남는다. 강사는 담당 반만 보낼 수 있다. 기존 학생 1명 발송은 그대로 둔다. 상세는 [FR-47 상세](#fr-47-상세).

#### FR-47 상세

- 대상: `GET /daily`와 같은 기준(그 날짜의 수강 등록)으로 정한다. 연락처가 하나도 없는 학생(학생만 골랐는데 학생 번호가 없는 경우 포함)은 대상에서 빠지고 확인 창에 이름이 나온다.
- 중복 방지: 같은 세션에 **성공(접수·대체 발송) 로그**가 있는 학생은 "이미 보냄"으로 표시하고 기본 제외한다. 테스트 모드 로그와 실패 로그는 세지 않는다(실패한 학생은 그대로 다시 보낼 수 있어야 하므로 — 구현 중 명확화).
- 순서·속도: 학생 ID 순서로 한 학생씩 보낸다. 중간에 서버가 재시작되면 작업은 `queued`로 돌아가 **아직 보내지 않은 학생부터** 이어서 보낸다(이미 로그가 남은 학생은 건너뛴다).
- 결과: 학생마다 성공(접수)·실패·테스트, 실패 사유. 작업 전체의 요약(대상·성공·실패·건너뜀)을 작업 결과에 남긴다.
- 다시 보내기: 결과 표의 [실패만 다시 보내기]는 실패한 학생만 대상으로 같은 조건의 새 일괄 작업을 만든다. 학생 1명 발송 화면의 실패 건에도 [다시 보내기]를 둔다(설계 흐름 5번).
- 알림톡: 템플릿을 고르면 전원 알림톡으로 보내고 실패 시 설정에 따라 문자 대체(FR-38)를 학생마다 적용한다.
- 한도: 한 작업의 대상은 최대 500명(알리고 개인·사업자 한도 안). 넘으면 거부하고 안내한다.
- **AC-49(신설) 반 단위 일괄 발송:** ① 학생 3명(한 명은 연락처 없음)인 반에서 [반 전체 발송]을 누르면 확인 창에 "대상 2명, 제외 1명(이름)"이 보인다 ② 등록하면 작업이 생기고 진행률이 오르다 완료되며 발송 로그에 학생 2명분이 각자의 본문으로 남는다(두 학생의 공통 구획은 같고 개별 구획은 다르다) ③ 한 학생의 발송이 실패하면 결과 표에 그 학생만 실패로 보이고 [실패만 다시 보내기]를 누르면 그 학생만 대상인 새 작업이 생긴다 ④ 같은 수업일에 다시 [반 전체 발송]을 열면 이미 보낸 학생이 기본 제외되어 대상 0명이고, 포함을 체크하면 다시 대상이 된다 ⑤ 테스트 모드에서는 외부 호출 없이 `test` 로그만 남고(AC-17) 이미 보냄 판정에 포함되지 않는다 ⑥ 강사가 담당하지 않는 반으로 등록하면 403이다 ⑦ 작업 도중 서버를 재시작하면 남은 학생부터 이어서 보내고 같은 학생에게 두 번 가지 않는다.

### 설계

- **REST 추가(메시지):**
  - `POST /messages/send-batch` — 본문 `{session_id, recipients: ["student"|"guardian"...], template_code?: string, student_ids?: number[], include_already_sent?: boolean}`. `student_ids`가 없으면 그 세션의 전원. 응답 `{task_id, planned: [{student_id, name}], skipped: [{student_id, name, reason: "no_recipient"|"already_sent"}]}`. 대상이 0명이면 422. 500명 초과 422. 권한은 `_visible_class`와 같다.
  - `GET /messages/send-batch/preview?session_id=&recipients=` — 확인 창용. 같은 `planned`·`skipped`를 작업 생성 없이 돌려준다.
  - 작업 상태는 기존 `GET /tasks/{task_id}`(DES-18). `result`에 `{sent, failed, test, skipped, students: [{student_id, name, status, channel, error}]}`를 담는다. `progress`는 처리한 학생 수 / 대상 수.
- **작업 처리(DES-09·DES-18):** `@task_handler("message_batch")`. 페이로드 `{campus_id, session_id, student_ids, recipients, template_code, actor_id}`. 학생마다 기존 1명 발송 함수를 **그대로 호출**하도록 `send_message`의 본문을 `_send_one(session, scope, payload)`로 분리하고 두 엔드포인트가 공유한다(중복 금지). 학생을 처리할 때마다 커밋하고 `progress`를 갱신한다. 재개 시 그 세션에 `test`가 아닌 로그가 있는 학생은 건너뛴다(AC-49 ⑦). 어댑터는 작업 시작 시 한 번 만든다.
- **권한:** 작업 생성 시 스코프 검사(캠퍼스·담당 반). 작업은 `actor_id`를 페이로드에 담고 처리 시 그 사용자의 스코프로 실행한다(`Scope` 재구성).
- **화면(`MessagesPage`):** 반·날짜 머리말 옆 [반 전체 발송] 버튼 → 대화상자(기존 `dialog` 컴포넌트): 수신 대상 체크(학생/학부모), 알림톡 템플릿 선택(기존 선택 재사용), `preview` 결과(대상 N명, 제외 목록, "이미 보낸 학생 N명 포함" 체크) → [N명에게 보내기] → 진행률 바(`GET /tasks/{id}` 2초 폴링) → 결과 표(학생·수신자·채널·상태·사유)와 [실패만 다시 보내기]. 학생 1명 발송의 결과 영역에도 실패 건 [다시 보내기]. 발송 내역 목록은 기존 그대로(새 로그가 보임).
- **데이터 모델(보정):** `message_log.session_id`(nullable, FK `class_session.id`, 인덱스) 추가 — 마이그레이션 `f7d1a5c9e3b6`. 단건·일괄 발송 모두 기록하고 이전 로그는 비어 있다. "이미 보냄"과 재개 건너뜀은 이 열로 판정한다. `background_task.kind`에 `message_batch` 값 추가(문자열).
- **성능:** 학생당 요청 1~2회, 320회면 수 분. 백그라운드라 화면은 막히지 않는다. 작업 큐는 단일 실행이라 시험지 분석과 순서대로 처리된다(동시 실행 없음 — 기존 설계).

## 대안 분석

| 대안 | 장점 | 단점·위험 | 판단 |
|---|---|---|---|
| A. 백그라운드 작업 + 학생별 순차 발송(기존 1명 발송 함수 재사용) | HTTP 시간 제한 없음, 재시작 재개, 학생별 결과, 코드 재사용 | 작업 큐가 단일 실행이라 분석 작업과 줄을 선다 | **채택** |
| B. 요청 안에서 동기 반복 | 단순 | 320회 외부 호출이 한 요청에 묶여 시간 초과·중간 끊김 시 어디까지 갔는지 모름 | 기각 |
| C. 알리고 대량 발송 API(`send_mass`, 수신자별 본문 500건/회) | 외부 호출 1회 | 응답이 성공·실패 **건수**뿐이라 수신자별 상태를 알 수 없어 FR-23의 수신자 단위 로그와 어긋남. 테스트 모드·알림톡·폴백과 경로가 갈라짐 | 기각 — 발송량이 커지면 재검토 |
| D. 화면에서 학생마다 1명 발송 API를 반복 호출 | 서버 변경 없음 | 브라우저를 닫으면 중단, 중복·누락 추적 불가 | 기각 |
| 이미 보낸 학생 처리: 경고만 | 단순 | 160명에게 두 번 나가면 요금 2배 | 기각 — 기본 제외 |

**ADR을 만들지 않는 이유:** ADR-005의 단일 발송 계약과 수신자 단위 로그를 그대로 쓰고, 기존 TaskRunner(DES-18)에 작업 종류를 더하는 변경이다.

## 검증 방법

- API(선행 테스트): preview의 대상·제외(연락처 없음·이미 보냄·테스트 로그 제외), 등록 시 작업 생성과 422(대상 0·500 초과), 작업 실행 후 학생별 로그·본문 개별성(AC-49 ②), 일부 실패 시 결과와 실패만 재등록(③), 재개 시 건너뜀(⑦, 로그 선삽입 후 실행), 테스트 모드 외부 호출 0(⑤), 강사 담당 외 403(⑥).
- 웹(선행 테스트): 대화상자 내용(대상·제외·포함 체크), 등록 호출 본문, 폴링 후 결과 표, [실패만 다시 보내기] 호출 본문, 단건 [다시 보내기].
- API·웹 전체, `npm run build`. 테스트 운영(테스트 모드)에서 고1 인A 7명 일괄 발송 → 로그 7건·결과 표 확인.

## 남은 위험과 미해결 사항

- 작업 큐가 단일 실행이라 시험지 분석 중이면 발송이 그 뒤에 시작된다. 운영 규모에서는 문제되지 않지만 안내 문구를 둔다.
- 알리고 응답은 "접수"다. 전달 실패 추적(`msg_id`)은 보류된 보완 3번에 남는다.
- 실발송 시험은 알리고 사업자 인증(갈래 A) 뒤에 가능하다. 그전에는 테스트 모드로 검증한다.
