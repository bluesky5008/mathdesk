## 요약

- 변경 분류: **요구사항 변경**(보안) — 사용자 관리(FR-02)에 비밀번호 변경·재설정을 더하고 데이터 모델에 칸 하나를 더한다.
- 변경 요지: ① 모든 사용자는 현재 비밀번호를 확인한 뒤 **자기 비밀번호를 바꿀 수 있다.** ② 원장은 같은 캠퍼스 사용자의 **비밀번호를 임시 비밀번호로 재설정**할 수 있다. ③ 원장이 정한 비밀번호(재설정·새 계정·최초 원장)로 로그인하면 **새 비밀번호를 정하기 전에는 다른 기능을 쓸 수 없다.**
- 사용자 결정(2026-09-24): "비밀번호 재설정도 함께 추가", 임시 비밀번호 **변경 강제**.
- 사용자 재승인 결과: 대기

## 변경 사유와 증거

- **계기:** 사용자가 DCR-008 검토 중 "비밀번호 재설정도 함께 추가"를 요청했다.
- **확인한 사실:**
  1. 비밀번호를 바꾸는 경로가 **하나도 없다** — 웹 화면도 API도 없다. 원장 비밀번호는 서버 설정 `MATHDESK_INITIAL_ADMIN_PASSWORD`로 최초 1회만 정해진다(`auth.ensure_initial_director`).
  2. 클라이언트 안내문(`docs/client/운영-이관-안내.md` 4장)은 이전 날 "정식 서버 원장 계정의 비밀번호를 핑수님이 직접 새로 정해 주세요"라고 약속했다. 지금은 지킬 수 없다.
  3. 원장이 강사 계정을 만들 때 초기 비밀번호를 원장이 정한다(`POST /users`). 강사가 이를 바꿀 수 없어 원장이 강사 비밀번호를 계속 알게 된다.
- **보류한 구현:** 없음.

## 제안 (기준선 `v10`)

### 요구사항

- **FR-02 보강:** 원장은 같은 캠퍼스 사용자의 비밀번호를 임시 비밀번호로 재설정할 수 있다. 모든 사용자는 현재 비밀번호를 확인한 뒤 자기 비밀번호를 바꿀 수 있다. 원장이 정한 비밀번호(새 계정, 재설정, 설정값으로 만든 최초 원장)로 로그인한 사용자는 새 비밀번호를 정하기 전에는 다른 기능을 쓸 수 없다.
- **AC-39(신설):** ① 현재 비밀번호가 맞으면 새 비밀번호로 바뀌고, 이전 비밀번호로는 로그인되지 않는다. 틀리면 바뀌지 않는다 ② 원장이 강사 비밀번호를 재설정하면 강사의 기존 로그인은 모두 끊기고, 임시 비밀번호로 로그인하면 비밀번호 변경 외의 요청이 거부된다 ③ 새 비밀번호를 정하면 정상적으로 쓸 수 있다 ④ 강사는 다른 사람의 비밀번호를 재설정할 수 없다.

### 설계

- **데이터 모델:** `app_user.must_change_password`(참·거짓, 기본 거짓) 추가. 기존 계정은 거짓(테스트 운영의 `director`/`director` 흐름은 바뀌지 않는다).
- **`POST /auth/password`(신설):** `{current_password, new_password}`. 현재 비밀번호 확인(틀리면 `400`, 로그인 실패 지연 규칙 적용), 새 비밀번호 8~128자·현재와 달라야 함(`422`). 성공 시 해시 저장, `must_change_password=거짓`, **이 세션을 뺀 본인의 다른 세션 삭제**, 감사 로그 `password.change`. `204`.
- **`POST /users/{id}/password`(신설, 원장 전용):** `{new_password}` 8~128자. 같은 캠퍼스 사용자만(아니면 `403`). 해시 저장, `must_change_password=참`, **그 사용자의 모든 세션 삭제**, 로그인 잠금 해제(실패 횟수·잠금 시각 초기화), 감사 로그 `password.reset`(대상 ID만, 비밀번호 값 없음). `204`. 원장 본인은 이 경로가 아니라 본인 변경을 쓴다(자기 대상이면 `422`).
- **변경 강제:** `must_change_password`가 참인 사용자는 `GET /auth/me`, `POST /auth/logout`, `POST /auth/password`만 쓸 수 있다. 나머지는 공통 스코프 검사(`current_scope`)에서 `403`("비밀번호를 먼저 바꿔 주세요")로 막는다 — 화면만이 아니라 서버가 막는다. `GET /auth/me`는 이 값을 알려 준다.
- **참으로 만드는 때:** `POST /users`로 만든 새 계정, `POST /users/{id}/password` 재설정, 설정값으로 새로 만든 최초 원장(운영 첫 로그인에서 원장이 직접 비밀번호를 정한다).
- **화면:** 로그인 후 `must_change_password`면 앱 대신 "새 비밀번호 설정" 화면만 보인다. 우측 상단 사용자 메뉴에 [비밀번호 변경]. 강사 계정 관리 화면(TASK-64)의 행마다 [비밀번호 재설정](확인 후 임시 비밀번호 입력).

## 대안 분석

| 대안 | 장점 | 단점·위험 | 판단 |
|---|---|---|---|
| A. 재설정 + 변경 강제 (선택) | 원장이 강사 비밀번호를 계속 알지 않는다. 운영 첫 로그인에서 원장도 직접 정한다 | 칸 1개·마이그레이션 | **채택**(사용자 선택) |
| B. 재설정만, 강제 없음 | 구조 변경이 없다 | 임시 비밀번호가 그대로 쓰일 수 있다 | 사용자가 A를 골랐다 |
| C. 이메일·문자로 재설정 링크 | 원장 개입이 없다 | 메일 발송 수단이 없고 문자 비용·실발송 검증이 필요하다. 소규모 학원에 과하다 | 기각 |

**ADR을 만들지 않는 이유:** 기존 인증 모델([ADR-007](./ADR-007-인증-권한-모델.md))의 세션·해시·스코프 구조 안에서 기능과 칸 하나를 더하는 변경이다.

## 마이그레이션과 롤백

- **마이그레이션:** `app_user.must_change_password BOOLEAN NOT NULL DEFAULT false`.
- **롤백:** 칸 삭제(downgrade), 엔드포인트·화면 제거.

## 검증 방법

- AC-39 ①~④ API 통합 테스트, 변경 강제 중 일반 API 403, 세션 무효화(다른 클라이언트의 쿠키가 401), 잠금 해제, 감사 로그에 비밀번호 값 없음, 최초 원장 생성 시 참.
- 웹: 강제 화면, 본인 변경, 재설정 흐름.
- 마이그레이션 왕복, 라우트 순회.

## 남은 위험과 미해결 사항

- 원장이 자기 비밀번호를 잊으면 복구할 화면 경로가 없다(다른 원장 계정이 재설정하거나, 서버에서 관리 명령으로 처리). 원장 계정을 두 개 두는 것을 권한다.
