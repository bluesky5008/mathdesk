## 요약

- 변경 분류: **요구사항 변경** — 반 삭제의 선행 조건(비활성)과 2단 확인(미리보기 창 + 이름 입력)을 없앤다. 반 삭제 API 계약(`confirm_name`, 활성 반 409)도 바뀐다.
- 변경 요지: 반 목록의 각 행에서 [수정] 오른쪽에 [삭제]를 두고(원장만), 누르면 활성·비활성과 관계없이 확인 없이 바로 하드 삭제한다. [수정] 창의 [삭제]도 같은 방식이다. 함께 지우는 범위(DCR-006)는 그대로다. 학생 삭제([DCR-012](./DCR-012-재원-학생의-바로-삭제.md)·[DCR-013](./DCR-013-학생-즉시-삭제.md))와 같은 방식이 된다.
- 사용자 지시(2026-10-11): "수정 우측에 삭제 버튼을 만들어서 바로 삭제할 수 있게 … 학생의 삭제와 동일하게 삭제 클릭시 바로 삭제되는 형태". 세부 선택: **활성 반도 바로 삭제**, **수정 창에서도 바로 삭제**.
- 사용자 재승인 결과: 대기

## 변경 사유와 증거

- **계기:** 사용자 지시(위). 지금은 반을 지우려면 [비활성] → [수정] → [삭제] → 건수 확인 → 이름 입력까지 거쳐야 한다.
- **확인한 사실:**
  1. 반 삭제는 이미 **하드 삭제**다 — 시간표·반 배정·그 반의 수업과 수업마다의 학생 일일 기록(출결·과제·진도)을 DB에서 지우고, 시험은 남기되 반 연결만 끊는다(`deletion.py` `delete_class`). 이번 변경의 실체는 선행 조건과 확인 절차 제거다.
  2. 활성 반의 `DELETE`는 409, 확인용 이름이 다르면 422다. 화면은 [수정] 창에서 비활성 반일 때만 [삭제]를 보이고, `DeleteDialog`(미리보기·이름 입력)를 띄운다. `DeleteDialog`를 쓰는 곳은 반 삭제뿐이다(학생은 DCR-013에서 뺐다).
  3. 테스트 운영(2026-10-11 조회): 반 5개 모두 활성. 고1 인A는 수업 12회·일일 기록 9건, 고1 인B는 수업 3회, 나머지 3개는 기록 없음. 반에 연결된 시험 0건.
- **보류한 구현:** 없음.

## 제안 (기준선 `v17`)

### 요구사항

- **FR-05 상세(삭제) 변경:** "반은 비활성일 때만 삭제할 수 있다"와 "반은 삭제 전에 함께 지워질 건수와 영향을 보여 주고, 이름을 입력해 확인받는다"를 지운다. 원장은 반을 활성 여부와 관계없이 삭제할 수 있고, [삭제]를 누르는 즉시 확인 없이 삭제된다. 함께 지우는 범위는 그대로다.
- **FR-07 변경:** "비활성 반은 원장이 삭제할 수 있다" → "원장은 반을 활성 여부와 관계없이 반 목록이나 [수정] 창의 [삭제]로 바로 삭제할 수 있다".
- **AC-36 개정:** "활성 반의 삭제 요청은 거부되고 데이터가 바뀌지 않는다"와 "반은 확인용 이름이 일치하지 않으면 삭제되지 않는다"를 지우고 다음으로 바꾼다 — 원장이 반 목록 행이나 [수정] 창의 [삭제]를 누르면 확인 없이 바로, 활성·비활성 어느 반이든 그 반의 시간표·반 배정·수업·일일 기록이 사라지고 연결된 시험과 결과는 남으며 다른 반의 데이터는 바뀌지 않는다. 강사 화면에는 반 [삭제]가 없고 API도 거부된다. (학생 부분은 그대로.)

### 설계

- **REST:** 반 `DELETE /classes/{id}`는 본문이 없다(와도 무시). 활성 반도 `204`로 지운다(409 없음). 원장만(강사 403), 캠퍼스 스코프는 공통 규칙.
- **미리보기:** `GET /classes/{id}/deletion-preview`는 계약만 유지한다(학생 미리보기와 같은 처리). 화면은 쓰지 않고, `deletable`은 항상 `true`다.
- **삭제 처리:** 한 트랜잭션에서 반 행을 잠그고 연관 데이터를 지운 뒤 반을 지운다(기존 그대로). 감사 로그 `class.delete`에 분류별 건수와 함께 **삭제 당시 활성 여부**(`is_active=true|false`)를 남긴다(학생의 삭제 당시 상태와 같은 이유 — 활성 반 삭제를 나중에 가려낼 수 있게).
- **화면:**
  - 반 목록 각 행 버튼: [명단] [비활성](활성일 때) [수정] **[삭제]**(원장만, 활성·비활성 모두). 누르면 확인 창 없이 바로 `DELETE`를 보내고 목록에서 빠진다.
  - [수정] 창의 [삭제]: 원장에게 활성 여부와 관계없이 보이고, 누르면 바로 지우고 창을 닫는다.
  - 삭제 미리보기·이름 입력 창(`DeleteDialog`)은 쓰는 곳이 없어지므로 지운다.
  - 강사에게는 행·창 어디에도 [삭제]가 없다(기존 그대로).

## 대안 분석

| 대안 | 장점 | 단점·위험 | 판단 |
|---|---|---|---|
| A. 활성 반도 확인 없이 즉시 삭제 (선택) | 학생 삭제와 같다. 한 번에 끝난다 | 오클릭 한 번에 그 반의 수업·일일 기록이 사라진다. 복구는 백업 복원뿐 | **채택** — 사용자 선택 |
| B. 비활성 반만 즉시 삭제 | [비활성]이 한 번의 안전장치가 된다 | 지금 반이 모두 활성이라 먼저 [비활성]을 눌러야 한다. 학생 삭제와 다르다 | 기각(사용자 선택) |
| C. 확인 창 한 번(이름 입력 없음) | 오클릭을 막는다 | 사용자가 학생과 같은 즉시 삭제를 원했다 | 기각 |

**ADR을 만들지 않는 이유:** DCR-013과 같이 확인 절차를 없애는 요구사항 변경이며 구조·저장 방식 결정이 아니다.

## 검증 방법

- API: 활성 반 본문 없이 `DELETE` → 204, 그 반의 시간표·배정·수업·일일 기록 삭제, 시험은 남고 `class_id`가 비며 다른 반은 그대로, 본문에 틀린 이름이 와도 삭제됨, 미리보기 `deletable=true`, 감사 로그 `is_active=true`, 강사 403, 다른 캠퍼스 403. 기존 "활성 반 409"·"이름 불일치 422" 테스트는 새 기준선에 맞춰 바꾼다.
- 웹: 원장 모든 행(활성·비활성)에 [수정] 오른쪽 [삭제], 클릭 즉시 `DELETE`·목록에서 빠짐·확인 창 없음, 수정 창 [삭제] 즉시 삭제·창 닫힘, 강사 화면에 [삭제] 없음. VER-35.

## 남은 위험과 미해결 사항

- **오클릭 보호가 없다**(사용자 선택). 활성 반을 잘못 지우면 그 반의 수업·일일 기록은 백업 복원으로만 돌아온다. 테스트 운영에는 자동 백업이 없다(TASK-57 대기).
