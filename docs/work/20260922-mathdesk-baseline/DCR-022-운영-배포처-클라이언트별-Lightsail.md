## 요약

- 변경 분류: **범위·요구사항·설계 변경** — 범위 밖이던 "Phase B(Kubernetes) 실제 배포"를 **클라이언트별 AWS Lightsail 단일 서버 + `docker compose` + Cloudflare 터널 운영(Phase B)**으로 정의해 범위에 넣고(ADR-013), 노출 표면 요구(NFR-17)를 테스트 운영/운영으로 나누며, 운영 데이터 보호(NFR-20)와 자동 백업(NFR-11 보강)을 요구사항화한다. 설계에 운영 서빙 컴포넌트(DES-25)를 더한다. 데이터 모델·REST 변경은 없다. [TASK-56](../../plan.md#task-56-운영-배포처-dcr)의 산출물이다.
- 변경 요지: ① 클라이언트(밤·핑수) 각자의 AWS 계정에 Lightsail 서버 1대씩, 같은 저장소·같은 `compose.prod.yaml`, `.env` 한 벌만 다름 ② 외부 경로는 클라이언트 Cloudflare 계정의 토큰 터널 하나, 호스트 포트 미게시, 방화벽 SSH만 ③ 백업은 클라이언트 계정 안에만(서버 내 일일 덤프 14일 + Lightsail 스냅샷 7개), 개발자 장비 복사 금지 ④ 테스트 운영(맥미니)은 스테이징으로 유지 ⑤ 이관 작업 TASK-57·59·60을 클라이언트 2명 기준으로 갱신.
- 사용자 결정 필요(가정으로 두고 승인 요청): **가정 1** 두 서버는 구성이 완전히 같고 `.env`만 다르다. **가정 2** 백업은 각 클라이언트 AWS 계정 안에만 두고 개발자 쪽 복사본은 두지 않는다. 다르면 수정 요청으로 알려 달라.
- 사용자 재승인 결과: **대기**

## 변경 사유와 증거

- **계기:** 사이클 3 이관 계획의 [TASK-56](../../plan.md#task-56-운영-배포처-dcr)이 "배포처 변경은 DCR이 먼저"로 묶여 있었고, 2026-10-11 작업 기록에 클라이언트 2명 기준으로 바꾸는 일이 보류되어 있었다. 사용자 요청(2026-10-11)으로 작성한다.
- **확인한 사실:**
  1. 요구사항 범위는 "Phase B(Kubernetes) 실제 배포"를 제외하고, NFR-08은 Phase A·B 동일 이미지를, NFR-17은 "인터넷 노출 구성은 **합성 데이터만** 보관"을 요구한다. 운영에는 실제 학생·학부모 정보가 들어가므로 NFR-17을 그대로 둘 수 없다.
  2. 클라이언트 2명(밤·핑수)이 각자 AWS 계정을 만들고 IAM 사용자 `yongs`로 콘솔 로그인·Lightsail 생성 화면·IAM 거부·결제 거부를 확인했다(작업 기록 2026-10-11). 두 사람은 각자 따로 운영한다.
  3. Lightsail 서울 $12 플랜(2GB·2vCPU·60GB·3TB, IPv4 포함), 자동 스냅샷 $0.05/GB-월·7개, 고정 IP는 붙어 있으면 무료(작업 기록의 AWS 조사). 테스트 운영의 유휴 메모리 합계는 약 360MB다.
  4. 터널은 `cfargotunnel.com` CNAME이 같은 Cloudflare 계정의 DNS만 프록시하므로 **클라이언트 계정 안의 원격 관리형(토큰) 터널**이어야 한다(도메인 안내문 작성 시 확인).
  5. 테스트 운영 compose는 `postgres`·`app`(정적 빌드 서빙)·`cloudflared`(config 파일 방식) 세 서비스이며 호스트 포트를 게시하지 않는다. 백업은 `ops/backup.sh`(pg_dump + files tar + SHA256)로 수동 실행한다. 자동 백업·보관 정책은 없다.
  6. 2026-10-11 사용자 결정: 문자 설정은 서버마다 환경변수 한 벌, 알리고는 학원 사업자 인증 경유(갈래 A).
  7. 서버에서 공개 저장소를 clone해 빌드하면 arm64→amd64 교차 빌드가 필요 없다(작업 기록 판단). Chromium·OpenCV 포함 이미지 빌드에 대비해 스왑 2GB를 둔다.
- **보류한 구현:** 없음(TASK-57 착수 전).

## 제안 (기준선 `v23`)

### 요구사항

- **범위 변경:** "Phase B(Kubernetes) 실제 배포 제외"를 삭제하고 포함 목록에 **Phase B 운영: 클라이언트별 AWS Lightsail 단일 서버 + `docker compose` + Cloudflare 터널([ADR-013](./ADR-013-운영-배포처-클라이언트별-Lightsail-단일-서버.md))**을 더한다. Kubernetes 전환은 범위 밖으로 남긴다(단, NFR-08의 "동일 이미지" 요구는 유지하므로 전환 가능성은 그대로다).
- **NFR-08 보강:** "Phase A·A′·B가 같은 저장소의 같은 compose 정의와 Dockerfile로 기동하며, 환경 차이는 `.env` 한 벌로 흡수한다. 운영 서버 사이에도 구성 차이를 두지 않는다."
- **NFR-11 보강:** "운영에서는 백업이 **자동으로 매일** 실행되고 최근 14일분이 서버 안에 보관되며, 서버 스냅샷이 별도로 7개 유지된다. 백업 결과를 사람이 확인하는 절차를 둔다. 복원은 빈 서버에 절차서만 보고 수행할 수 있어야 한다."
- **NFR-17 분리:** 노출 표면 통제(포트 미게시·기본 비밀번호 금지)는 모든 노출 구성에 적용하고, "합성 데이터만 보관"은 **테스트 운영(Phase A′)에만** 적용한다.
- **NFR-20(신설) 운영 데이터 보호:** 운영 서버의 학생·학부모 정보와 백업은 **클라이언트 명의 AWS 계정 안에만** 존재한다. 백업 파일은 소유자만 읽을 수 있고(권한 600), 스냅샷은 AWS 저장 시 암호화를 쓴다. 개발자는 클라이언트가 발급한 IAM 사용자(MFA)와 SSH 키로만 접근하고 운영 데이터를 개발자 장비로 복사하지 않는다. 초기 원장 비밀번호는 이관 당일 클라이언트가 직접 바꾼다. 클라이언트는 IAM 사용자 비활성화와 SSH 키 교체로 개발자 접근을 언제든 회수할 수 있어야 한다.
- **AC-48(신설) 운영 서버:** ① 클라이언트 도메인으로 HTTPS 로그인이 되고 쿠키에 `Secure`·`HttpOnly`가 있다 ② Lightsail 방화벽에 SSH 외 입력 규칙이 없고 `docker compose ps`에 게시된 호스트 포트가 없다 ③ 자동 백업이 다음 날 생성되고 14일보다 오래된 백업이 지워진다 ④ 백업으로 빈 컨테이너에 복원하면 행 수와 파일 체크섬이 같다 ⑤ 두 클라이언트 서버가 같은 커밋·같은 이미지 다이제스트를 쓴다 ⑥ 초기 원장 비밀번호 변경 뒤 이전 비밀번호로 로그인되지 않는다 ⑦ 문자 실발송 1건이 클라이언트 번호에 도착하고 발송 내역에 `접수`로 남는다.

### 설계

- **DES-25(신설) 운영 서빙 — 클라이언트별 서버:** [ADR-013](./ADR-013-운영-배포처-클라이언트별-Lightsail-단일-서버.md) 결정 1~6. 구성 요소와 책임은 다음과 같다.

| 요소 | 내용 |
|---|---|
| `compose.prod.yaml` | `postgres`(볼륨 `pgdata`), `app`(`Dockerfile.testops`와 같은 이미지, 정적 빌드 서빙, 볼륨 `files`), `cloudflared`(`tunnel --no-autoupdate run`, `TUNNEL_TOKEN` 환경변수). 호스트 포트 없음. 시드 없음. `restart: unless-stopped` |
| `.env`(서버, 600) | `POSTGRES_PASSWORD`, `MATHDESK_INITIAL_ADMIN_*`, `MATHDESK_COOKIE_SECURE=true`, `CLOUDFLARE_TUNNEL_TOKEN`, `MATHDESK_MESSAGING_MODE`·`ALIGO_*`, `MATHDESK_LLM_*`·`ANTHROPIC_API_KEY`(또는 OpenAI 호환 키). 테스트 운영 compose가 LLM 변수를 전달하지 않던 누락을 운영 compose에서 해소 |
| 서버 | Lightsail 서울 2GB, Ubuntu LTS, Docker, 스왑 2GB, 고정 IP, 자동 보안 업데이트, 자동 스냅샷(7개). 방화벽 SSH만(가능하면 개발자 IP 한정) |
| 배포 | `git pull` → `ops/backup.sh`(운영 프로필) → `docker compose -f compose.prod.yaml up -d --build` → `/api/health`·로그인 스모크. 스키마 변경 시 백업 선행은 기존 규칙 |
| 백업 | `ops/backup.sh`를 `PROJECT`·compose 파일 인자로 운영 프로필화, cron(매일 04:00) → `/var/backups/mathdesk/<일시>/`, 14일 지난 폴더 삭제, 결과를 로그 파일에 남김. 확인은 TASK-60 절차 |
| 복원·롤백 | `ops/restore.sh` 운영 프로필. 앱 롤백은 이전 커밋 체크아웃 후 재빌드, 스키마는 `alembic downgrade` 또는 백업 복원. 서버 전체는 스냅샷 복원 |
| 스테이징 | 맥미니 테스트 운영이 모든 변경을 먼저 받는다. 운영 배포는 스테이징 확인 뒤 같은 커밋으로 |
| 접근 | IAM `yongs`(Lightsail 정책, MFA), SSH 키. 서버당 1벌. 인계 절차: 키 교체·IAM 비활성화 |

- **보안과 품질 속성 표 갱신:** "노출 표면" 행을 테스트 운영/운영으로 나누고, "가용성" 행에 단일 서버·스냅샷·수동 복구를 명시한다. "비밀 정보" 행에 서버 `.env` 한 벌·저장소 외 보관을 더한다.
- **마이그레이션과 롤백 절 갱신:** Phase A→B 전환은 "테스트 운영 데이터를 옮기지 않고 빈 DB + 초기 원장으로 시작"으로 확정. 운영 롤백 절차를 위 표대로 명시.
- **데이터 모델·REST:** 변경 없음.

## 마이그레이션과 롤백

- **마이그레이션:** 데이터 이관 없음(빈 DB + 초기 원장). 스키마는 `alembic upgrade head`.
- **롤백:** 운영 서버를 끄고 테스트 운영으로 돌아갈 수 있다(운영 데이터는 클라이언트 계정 스냅샷에 남는다). 코드 변경(compose 파일·스크립트)은 되돌리기만.

## 검증 방법

- TASK-57: 로컬에서 `compose.prod.yaml` 기동·전체 스모크, 백업 cron 스크립트 1회 수행·보관 정리 확인, 복원 리허설(AC-48 ③④의 로컬판).

- TASK-60: 첫 1~2주 자동 백업 생성·AWS 청구액·오류 로그 확인.

## 남은 위험과 미해결 사항

- 단일 서버라 장애 시 수동 복구다(ADR-013 단점). 복구 시간 목표는 두지 않는다(요구 없음).
