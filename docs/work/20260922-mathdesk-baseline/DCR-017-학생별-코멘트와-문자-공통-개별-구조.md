## 요약

- 변경 분류: **요구사항 변경** — 학생 일일 기록에 코멘트 칸을 더하고(데이터 모델·API 변경), 문자 본문을 "반 공통 → 학생 개별" 순서로 바꾸며 강사 첨언을 공통 코멘트로 문자에 넣는다(FR-18 구획·AC-14 변경).
- 변경 요지: 일일 입력 표 맨 오른쪽(테스트 다음)에 **학생별 코멘트** 한 줄 입력 칸. 문자는 위에 그날 반 공통 내용(진도·오늘의 과제·영상 링크·**선생님 코멘트**=강사 첨언), 아래에 학생 개별 내용(출결·과제피드백·테스트·**개별 코멘트**)을 붙여 학생마다 다르게 나간다. 받는 사람은 기존 그대로 학생·학부모·둘 다를 체크해 각자의 번호로 보낸다.
- 사용자 결정(2026-10-11): ① 강사 첨언을 **공통 코멘트로 문자에 넣음** ② 본문 순서 **공통 먼저, 개별 나중** ③ 코멘트 칸은 **한 줄 입력**(방향키·Enter로 다음 학생, [표 저장]으로 저장)
- 사용자 재승인 결과: **승인 (2026-10-11)** — 기준선 `v17` → `v18` 발행

## 변경 사유와 증거

- **계기:** 사용자 요청(2026-10-11) — 문자로 통보할 때 공통 데이터 + 학생별 피드백을 붙여 보내고, 학생별 코멘트를 일일 입력 표에서 입력하고 싶다.
- **확인한 사실:**
  1. 문자 본문은 이미 학생마다 만든다(`messaging.render_daily_message`) — 제목·출결·진도·과제피드백·테스트·오늘의 과제·영상 링크 7구획(FR-18 상세). **학생별 자유 코멘트 칸은 없다.**
  2. 일일 입력의 "오늘 진도 & 코멘트" 카드에는 진도 1~4교시·오늘의 과제·영상 링크·**강사 첨언**(`class_session.teacher_note`)이 있다. 이 중 **강사 첨언만 문자에 들어가지 않는다.** 테스트 운영의 첨언은 0건이다(2026-10-11 조회) — 문자에 넣어도 기존 내용이 새로 노출되지 않는다.
  3. 발송 대상 선택은 **이미 구현되어 있다**: 알림문자 화면의 [학생]·[학부모] 체크 → `POST /messages/send`의 `recipients`가 `student`면 학생 번호, `guardian`이면 통보 대상 보호자 번호(DCR-014의 학부모 연락처), 둘 다면 양쪽에 같은 본문으로 보낸다. 이 DCR은 이 동작을 바꾸지 않고 인수 조건으로 고정만 한다.
  4. 리포트 카드(ADR-011)는 요약(출결·과제·테스트)을 위에, 상세(진도·과제·영상)를 아래에 두는 확정 레이아웃이다. `report._sections`는 쓰는 곳이 없다(범위 밖 발견).
  5. 알림톡 템플릿 변수는 `ALIMTALK_FIELDS`가 정한다. 테스트 운영에 등록된 알림톡 템플릿은 0건이다.
- **보류한 구현:** 없음(구현 시작 전).

## 제안 (기준선 `v18`)

### 요구사항

- **FR-44(신설) 학생별 코멘트:** 일일 입력 표의 맨 오른쪽(테스트 다음) 칸에 학생마다 그날의 코멘트를 한 줄로 적는다(500자 이내, 비울 수 있음). 다른 칸처럼 방향키·Enter로 다음 학생으로 이동하고 [표 저장]으로 저장한다. 출결 확정(잠금)과 관계없이 입력할 수 있다(과제·테스트와 같음). 강사는 담당 반에서만 입력한다(기존 일일 기록 권한).
- **FR-14 상세 변경:** 표 일괄 저장 대상에 **학생별 코멘트**를 더한다.
- **FR-18 상세 변경 — 본문 구획과 순서:**
  1. 제목(학생명 + 학습피드백), 학원명·강사명 인사말, 수업일
  2. **반 공통** — `■ 수업진도`(교시별) · `■ 오늘의 과제` · `■ 수업 영상 링크` · `■ 선생님 코멘트`(강사 첨언)
  3. **학생 개별** — `■ 출결` · `■ 과제피드백`(등급과 등급 문구) · `■ 테스트`(시험명·학생 점수·반 평균) · `■ 개별 코멘트`
  - 데이터가 없는 구획은 생략한다(기존 규칙). 렌더 시점 생성·발송 시 스냅샷(기존 규칙).
- **AC-14 변경:** 모든 값이 있는 학생의 미리보기는 9개 구획(진도·오늘의 과제·영상 링크·선생님 코멘트·출결·과제피드백·테스트·개별 코멘트 + 제목)을 **이 순서로** 포함하고, 테스트가 없으면 테스트 구획이, 코멘트가 없으면 해당 코멘트 구획이 생략된다.
- **AC-43(신설):** ① 일일 입력 표에서 두 학생에게 서로 다른 코멘트를 적고 [표 저장]하면 다시 열었을 때 그대로 보인다 ② 같은 날 두 학생의 문자 미리보기는 공통 구획(진도·과제·영상·선생님 코멘트)이 같고, 개별 코멘트는 각자 적은 내용이다 ③ 코멘트가 500자를 넘으면 저장이 거부된다 ④ 출결 확정 후에도 코멘트를 저장할 수 있다 ⑤ 발송 대상 [학생]만 고르면 학생 번호로, [학부모]만 고르면 그 학생의 학부모 번호로, 둘 다 고르면 두 번호 모두로 같은 본문이 발송되고 발송 로그에 수신자 유형별로 남는다 ⑥ 리포트 카드에도 선생님 코멘트와 개별 코멘트가 보인다.

### 설계

- **데이터 모델:** `student_daily_record.comment`(text, NULL 허용) 추가 — 마이그레이션 1건(nullable 열 추가, 기존 행 영향 없음).
- **REST(추가만, 하위 호환):**
  - `PUT /daily/{session_id}/records`의 `RecordIn`에 `comment`(500자 이내, NULL 허용). 기존 규칙대로 **보내지 않으면 건드리지 않는다**. 빈 문자열은 NULL로 저장한다.
  - `GET /daily`의 학생 기록 출력에 `comment`.
- **메시지 렌더러(DES-07):** `MessageContext`에 `teacher_note`(공통)·`student_comment`(개별)를 더하고 `render_daily_message`의 구획 순서를 위 FR-18 상세대로 바꾼다. 렌더러는 순수 함수 그대로다.
- **알림톡 변수:** `ALIMTALK_FIELDS`에 `teacher_note`(선생님 코멘트)·`student_comment`(개별 코멘트)를 더한다. `daily_message`(일일 피드백 전체)는 새 순서를 따른다. 등록된 템플릿이 없어 기존 템플릿 영향은 없다.
- **리포트 카드(DES-08, ADR-011 유지):** 요약 우선 레이아웃은 그대로 두고, 요약(출결·과제·테스트) 바로 아래에 **개별 코멘트** 상자, 상세(진도·과제·영상) 끝에 **선생님 코멘트**를 더한다. 카드는 학부모가 점수를 먼저 보도록 설계된 별도 형식이라 문자의 순서를 따르지 않는다 — AC-16의 "본문과 동일한 내용"은 그대로 충족한다.
- **발송:** 변경 없음. 학생마다 본문을 따로 만들고, 선택한 수신자 유형별 번호로 같은 본문을 보낸다(`_recipients_for`). 본문이 길어지면 기존 규칙대로 SMS 대신 LMS가 된다.
- **화면:**
  - 일일 입력: 표 열 `학생 | 출결 상태 | 이전 과제 재검사 | 과제피드백 | 테스트 | 코멘트`. 코멘트는 한 줄 `Input`(넓게, `maxLength` 500), 키보드 그리드의 한 열로 들어간다. 대시보드 출결 위젯에는 넣지 않는다(출결 전용).
  - "오늘 진도 & 코멘트" 카드의 [강사 첨언] 칸 이름을 **[선생님 코멘트 (문자 공통)]**으로 바꿔 문자에 나간다는 것을 알린다.
  - 알림문자 화면: 변경 없음(미리보기가 새 본문을 보여 준다). 발송 대상 체크박스는 기존 그대로.

## 대안 분석

| 대안 | 장점 | 단점·위험 | 판단 |
|---|---|---|---|
| A. `student_daily_record`에 `comment` 열 (선택) | 그날·그 학생 기록과 한 행이라 저장·조회·삭제(학생·반 삭제)가 기존 경로를 그대로 탄다 | 없음 | **채택** |
| B. 별도 `student_comment` 테이블 | 코멘트 이력을 여러 건 둘 수 있다 | 하루 한 건이면 충분하다. 저장 단위·삭제 경로를 새로 만들어야 한다 | 기각 |
| C. 상담일지(`consult_log`)에 기록 | 기존 기능 재사용 | 상담일지는 날짜·수업과 묶이지 않고 문자 경로가 없다. 의미가 다르다 | 기각 |
| 본문 순서: 기존 순서 + 맨 아래 코멘트 | 기존 문자와 같아 보인다 | 사용자가 공통 먼저를 골랐다 | 기각(사용자 결정) |
| 코멘트 칸: 여러 줄 | 줄바꿈 가능 | 그 칸에서 Enter가 줄바꿈이 되어 키보드 이동(NFR-13)이 끊긴다 | 기각(사용자 결정) |

**ADR을 만들지 않는 이유:** 기존 테이블에 nullable 열 하나와 입출력 필드를 더하고 렌더 순서를 바꾸는 변경이며, 저장 방식·구조·카드 렌더링 방식(ADR-011) 결정을 바꾸지 않는다.

## 마이그레이션과 롤백

- **마이그레이션:** `student_daily_record.comment` nullable 열 추가. 배포 전 백업.
- **롤백:** 코드를 되돌리고 다운그레이드로 열을 지운다. **열을 지우면 입력한 코멘트가 사라진다** — 롤백 전 백업. 발송 로그의 스냅샷은 영향 없다.

## 검증 방법

- API: 코멘트 저장·조회, 생략 시 불변, 빈 값 NULL, 501자 422, 확정 후 저장 가능, 강사 담당 반 외 403(기존), 렌더러 9구획 순서·생략 규칙(AC-14), 같은 날 두 학생 공통 같음·개별 다름(AC-43 ②), 수신자 유형별 발송·로그(AC-43 ⑤), 알림톡 새 변수, 리포트 카드 HTML에 두 코멘트(AC-43 ⑥), 마이그레이션 왕복.
- 웹: 코멘트 칸 입력 → [표 저장] 본문에 `comment`, 키보드 이동(다음 학생 코멘트 칸), 확정 후 입력 가능, 카드 칸 이름.
- 공개 주소: 테스트 데이터(고1 인A)로 미리보기 확인(발송은 테스트 모드).

## 남은 위험과 미해결 사항

- LMS는 2,000바이트(한글 약 1,000자)까지다. 공통·개별 코멘트가 모두 길면 본문이 이를 넘어 발송이 실패할 수 있다 — 기존에도 진도·과제 길이로 같은 위험이 있었다. 지금은 코멘트 500자 제한만 두고, 필요해지면 미리보기에 바이트 수 경고를 따로 만든다.
- 학부모가 둘 이상이면 통보 대상 모두에게 간다(기존 규칙).
- `report._sections`는 쓰지 않는 함수다. 이 DCR 구현에서 순서가 바뀌면 오해를 부르므로 함께 지울지 구현 계획에서 정한다(동작 영향 없음).
