## 요약

- 결정: 웹 UI에 **Tailwind CSS v4 + shadcn/ui 패턴(Radix primitives) + Recharts**를 도입하고, 색·간격·타이포·라운드·그림자를 **CSS 변수 단일 소스(`tokens.css`)**로 정의한다. 이 토큰은 리포트 카드 템플릿이 함께 사용한다.
- 핵심 이유: 이 앱은 밀도 높은 업무 도구이며, 심미성은 장식이 아니라 타이포 스케일·간격 리듬·표 가독성·포커스 상태에서 나온다. shadcn/ui는 컴포넌트 소스를 저장소에 복사하므로 NFR-13(표 기반 입력·키보드 이동)의 특수 요구를 컴포넌트 내부에서 맞출 수 있다.
- 주요 단점: JSX 클래스 문자열이 길어지고, 컴포넌트 소스가 저장소로 들어와 코드량이 늘며, 기존 화면 5개를 전면 재작성한다.

## 배경

현재 웹 앱에는 **스타일이 전혀 없다**. 실측 결과 CSS 파일 0개, `className`·`style` 사용 0회, 스타일 라이브러리 0개다. 화면 전체가 브라우저 기본 스타일로 렌더된다.

기준선에 디자인·미관 요구사항이 없다. UI 관련 항목은 [NFR-13](../../requirements.md#비기능-요구사항)(한국어 UI·표 기반 입력·키보드 이동 — 조작 효율)과 [NFR-14](../../requirements.md#비기능-요구사항)(1280px 이상 지원 — 해상도)뿐이며, 설계 문서에는 CSS·디자인·스타일이 한 번도 등장하지 않는다. 의도적 제외가 아니라 요구사항 도출 단계에서 다루지 않은 항목이다.

사용자가 매출 확대 목표를 밝혔고, 범위를 "지금 공통 기반 + 화면별 다듬기까지"로, 판단 기준을 "변경 범위가 커지더라도 기능적으로 가장 좋고 미관적으로 가장 이쁜 솔루션"으로 지정했다.

**재작성 위험이 낮다는 근거:** 웹 테스트 20건의 쿼리가 전부 의미 기반이다(`getByRole` 15, `getByLabelText` 5, `getByText` 10, `getByTestId`·`querySelector`·`container` 각 0). 역할과 레이블을 유지하면 마크업을 전면 교체해도 테스트가 그대로 통과한다.

## 영향을 받는 요구사항과 제약

- [NFR-13](../../requirements.md#비기능-요구사항): 마우스 이동을 최소화하는 표 기반 입력과 키보드 이동. **일반적이지 않은 요구이며 이 결정의 핵심 제약이다.**
- [NFR-14](../../requirements.md#비기능-요구사항): 1280px 이상 데스크톱. 모바일 반응형 불필요.
- [NFR-12](../../requirements.md#비기능-요구사항): 테스트 가능성. 기존 테스트 20건을 깨지 않아야 한다.
- 스택 제약: React 19 + Vite 6 + TypeScript([ADR-001](./ADR-001-기술-스택과-실행-형태.md)).
- [ADR-011](./ADR-011-리포트-카드-HTML-렌더링.md)이 같은 토큰을 사용한다. 토큰은 프레임워크에 묶이지 않은 순수 CSS 변수여야 한다.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| A. Tailwind v4 + shadcn/ui 패턴 + Recharts (선택) | 컴포넌트 소스가 저장소에 있어 NFR-13 특수 요구를 내부에서 해결. Radix로 접근성·키보드 기본 제공. 토큰이 설정에 강제되어 화면 간 일관성 자동 유지. 차트까지 한 언어 | 클래스 문자열이 길다. 코드량 증가. 빌드 설정 추가 | 높음(전 화면 재작성) |
| B. UI 컴포넌트 라이브러리(Mantine·MUI) | 표·폼·모달이 즉시 갖춰짐. 초기 속도 가장 빠름 | **라이브러리 API 밖 요구가 나오면 싸워야 한다.** 이 앱의 핵심 화면이 정확히 그 특수 요구(표 기반 키보드 입력)다. 번들이 크고 룩이 라이브러리에 종속 | 높음 |
| C. 순수 CSS + 디자인 토큰 | 의존성 0. 되돌리기 가장 쉬움 | 컴포넌트·접근성·차트를 전부 직접 만든다. 일관성을 사람의 규율에 의존 | 중간 |
| D. 현행 유지(무스타일) | 비용 0 | 사용자 목표를 충족하지 못한다 | 없음 |

B를 기각하는 이유가 이 결정의 중심이다. 라이브러리는 표준적인 화면을 빨리 만들지만, 이 앱에서 매일 쓰이는 화면은 표준적이지 않다. C는 심미 목표에는 도달할 수 있으나 12개 화면의 일관성을 보장할 장치가 없다.

## 결정

1. **Tailwind CSS v4**(`tailwindcss` + `@tailwindcss/vite`)를 도입한다. Vite 플러그인 하나로 붙으며 별도 PostCSS 설정이 필요 없다.

2. **디자인 토큰을 `apps/web/src/styles/tokens.css`에 CSS 변수로 단일 정의한다.** 색·간격·타이포 스케일·라운드·그림자. Tailwind v4는 `@theme`로 이 변수를 읽는다. 이 파일은 프레임워크에 묶이지 않은 순수 CSS이므로 [ADR-011](./ADR-011-리포트-카드-HTML-렌더링.md)의 카드 템플릿이 그대로 인라인한다.

3. **shadcn/ui 패턴으로 공통 컴포넌트를 저장소에 둔다.** 라이브러리 의존이 아니라 소스 복사다. 필요한 primitive만 `@radix-ui/*`로 추가하고, `class-variance-authority`·`tailwind-merge`·`clsx`로 변형을 관리한다. 아이콘은 `lucide-react`.

4. **차트는 Recharts**를 사용한다. TASK-25·26 통계 화면에 필요하며, 지금 정하면 그 시점에 결정을 미루지 않는다.

5. **표 기반 입력 컴포넌트는 직접 소유한다.** NFR-13의 키보드 이동·즉시 저장 동작은 공통 컴포넌트 내부에 구현하고, 라이브러리 동작에 맞추지 않는다.

6. **의미 구조를 보존한다.** 재작성 시 역할(`role`)과 레이블을 유지해 기존 테스트 20건이 그대로 통과해야 한다. 통과하지 않으면 마크업이 잘못된 것으로 본다.

7. **다크 모드는 토큰 레벨에서 지원하되 초기 기본값은 라이트다.** 1280px 이상 데스크톱 전용이므로 모바일 반응형은 범위 밖이다.

## 이유

1. 밀도 높은 업무 도구의 심미성은 컴포넌트의 화려함이 아니라 스케일과 리듬의 일관성에서 나온다. 토큰을 설정에 강제하는 방식이 이 목표에 직접 기여한다.
2. NFR-13은 라이브러리로 해결되지 않는다. 소스를 소유하는 방식만이 이 요구를 정면으로 만족시킨다.
3. Radix의 포커스 관리·키보드 내비게이션·ARIA는 테스트가 `getByRole` 기반인 이 저장소와 방향이 일치한다. 접근성이 좋아질수록 테스트가 안정된다.
4. 토큰을 순수 CSS 변수로 두면 웹과 리포트 카드가 하나의 브랜드 언어를 공유한다. 이것이 [DCR-003](./DCR-003-브랜드-자산으로서의-시각-설계.md)의 매출 목표에 직접 연결된다.

## 결과와 감수할 단점

- 새 의존성이 늘어난다: `tailwindcss`, `@tailwindcss/vite`, `recharts`, `class-variance-authority`, `tailwind-merge`, `clsx`, `lucide-react`, 필요한 `@radix-ui/*`. 조회 시점(2026-09-23) 기준 모두 현행 버전이 존재한다.
- JSX 가독성이 떨어진다. 반복 패턴은 공통 컴포넌트로 흡수해 완화한다.
- 기존 5개 화면을 전면 재작성한다. 테스트가 의미 기반이라 회귀 위험은 낮지만 작업량은 실재한다.
- 웹 번들 크기가 증가한다. 1280px 데스크톱 전용이며 사내망 수준 사용이라 수용 가능하다.
