## 변경 사유와 증거

- **계기:** 사용자 요청(2026-10-11). 학생의 학교를 텍스트로 치지 않고 드롭다운으로 고르려 한다. 이를 위해 학교 목록을 관리하는 기능이 함께 필요하다.
- **확인한 사실:**
  1. 학교는 `student.school`(문자열 100자, NULL 허용)에 자유 텍스트로 저장된다(`models/masterdata.py`). 학생 입출력 `StudentIn`·`StudentOut`의 `school`도 문자열이다(`masterdata.py`).
  2. 학교를 읽는 곳은 학생 API·학생 화면·시드(`seed.py`)뿐이다. 통계·리포트·발송·OMR은 학교를 쓰지 않는다. 학생 검색(`q`)은 이름만 본다.
  3. 학년 드롭다운(TASK-79)은 목록이 코드에 고정되어 있고 서버는 자유 문자열 그대로다. 학교는 원장이 목록을 바꿔야 하므로 같은 방식을 쓸 수 없다.
  4. 테스트 운영 데이터: 캠퍼스 1곳, 학생 26명의 학교 값은 시드가 넣은 "고1학교"(9)·"고2학교"(11)·"고3학교"(6) 3종이다.
- **보류한 구현:** 없음.

## 제안 (기준선 `v16`)

### 요구사항

- **FR-43(신설) 학교 관리:** 원장은 캠퍼스의 학교를 이름으로 등록·수정·삭제할 수 있어야 한다. 학교 이름은 캠퍼스 안에서 겹치지 않는다(앞뒤 공백은 지우고 비교, 1~100자). 목록은 가나다순이고 학교마다 그 학교 학생 수(재원 상태와 관계없이 전체)를 보인다. 이름을 바꾸면 그 학교 학생 모두에게 새 이름이 보인다. 학생이 있는 학교도 바로 삭제되며, 그 학생들의 학교는 비고 다른 정보는 그대로다. 강사는 학교를 관리하지 않는다.
- **FR-05 보강:** 학생의 학교는 FR-43에 등록된 학교 중에서 고른다(비워 둘 수 있다). 등록된 학교가 없으면 학교 탭에서 먼저 등록하라고 안내한다.
- **AC-42(신설):**
  1. 원장이 [학교] 탭에서 이름을 넣고 등록하면 가나다순 목록에 보인다. 같은 이름(앞뒤 공백 무시)이나 빈 이름은 거부된다.
  2. 학생 등록 한 줄과 수정 창의 학교 칸은 드롭다운이며 등록된 학교와 "선택"(비움)만 고를 수 있다. 고르고 저장하면 학생 목록의 학교 열에 그 이름이 보인다. 다른 캠퍼스의 학교나 없는 학교로 저장하려 하면 거부된다.
  3. 학교 이름을 바꾸면 그 학교 학생들의 학교 열이 새 이름으로 보인다. 다른 학교와 같은 이름으로 바꾸면 거부된다.
  4. 학생이 있는 학교를 삭제하면 확인 없이 삭제되고, 그 학교 학생들의 학교가 비며 이름·학년·연락처·성적 등 다른 정보는 그대로다. 삭제는 감사 로그에 학교 이름과 비워진 학생 수로 남는다.
  5. 강사에게는 [학교] 탭이 보이지 않고, 학교 API를 부르면 거부된다.
  6. 마이그레이션 후 기존 학생은 같은 이름의 학교에 연결되어 학교 열 표시가 이전과 같다. 다운그레이드하면 학교 이름이 학생의 텍스트 칸으로 돌아온다.
  7. 등록된 학교가 없으면 학생 등록 줄의 학교 드롭다운 아래에 학교 탭에서 먼저 등록하라는 안내와 탭으로 가는 링크가 보인다.

### 설계

- **데이터 모델:**
  - `school`(신설): `id`, `campus_id`(FK `campus`, 색인), `name`(문자열 100자). 유일 제약 `(campus_id, name)`.
  - `student.school_id`(신설): FK `school.id`, NULL 허용, 색인, `ON DELETE SET NULL`.
  - `student.school`(문자열) **삭제** — 이름이 두 곳에 갈라지지 않게 한다. 학생 출력의 학교 이름은 조인해서 준다.
- **REST:**
  - 학교(신설, 모두 원장 전용 — 강사는 403, 캠퍼스 스코프):
    - `GET /schools` → `[{id, name, student_count}]`, 이름순. 학생 수는 한 번의 집계 조회로 함께 읽는다.
    - `POST /schools` `{name}` → 201. 이름은 앞뒤 공백을 지운 뒤 1~100자(아니면 422), 같은 캠퍼스에 같은 이름이 있으면 409 "이미 등록된 학교입니다."
    - `PATCH /schools/{id}` `{name}` → 같은 검증. 다른 캠퍼스나 없는 id는 403(REST 공통 규칙 — 자원 존재 여부를 노출하지 않음).
    - `DELETE /schools/{id}` → 204. 한 트랜잭션에서 그 학교 학생들의 `school_id`를 NULL로 바꾸고 학교를 지우며, 감사 로그 `school.delete`(대상 `school:{id}`, 상세 "이름, 학생 N명")를 남긴다.
  - 학생(변경): `StudentIn`의 `school`(문자열)을 `school_id`(정수, NULL 허용)로 바꾼다. 저장할 때 그 id가 같은 캠퍼스의 학교가 아니면 422 "학교를 찾을 수 없습니다." `StudentOut`은 `school_id`와 `school`(학교 이름, 읽기 전용)을 함께 준다 — 목록·다른 화면의 학교 표시는 그대로 `school`을 쓴다. `GET /students`는 학교 이름을 같은 조회에서 조인해 읽는다(학생 수만큼 추가 조회 없음).
  - **호환성:** 학생 입력의 `school` 문자열은 더 이상 받지 않는다(보내도 무시된다). 이 API를 부르는 곳은 이 저장소의 웹 화면뿐이며 같은 배포로 함께 바뀐다.
- **권한:** 학교 관리는 원장 전용(FR-43). 강사는 학생을 등록·수정하지 않으므로 학교 목록 API가 필요 없다. 강사에게 보이는 학교 정보는 지금처럼 학생 목록의 학교 이름뿐이다(새 노출 없음).
- **화면:**
  - **[학교] 탭**(`/students/schools`, 원장에게만 보임): 위에 등록 한 줄(학교 이름 + [학교 등록]), 아래에 표(학교 이름 · 학생 수 · [수정] [삭제]). [수정]을 누르면 그 행의 이름이 입력 칸이 되고 [저장]·[취소]가 나온다. [삭제]는 확인 없이 바로 지운다. 저장 실패(중복 등)는 그 자리에 오류 문구로 보인다.
  - **학생 등록 한 줄·수정 창:** 학교 칸이 드롭다운("선택" + 등록된 학교 이름순)이 된다. 등록된 학교가 없으면 등록 줄의 드롭다운 아래에 "학교 탭에서 먼저 학교를 등록하세요"와 탭 링크를 보인다.
  - 학생 목록의 학교 열은 지금처럼 이름을 글자로 보인다(목록에서 바로 바꾸는 드롭다운은 이 DCR 범위 밖).
  - 학교를 등록·수정·삭제하면 학교 목록과 학생 목록 조회를 새로 고쳐 바뀐 이름·빈칸이 바로 보인다.
- **시드:** 시드는 학교를 먼저 만들고 학생을 그 학교에 연결한다.
- **삭제:** 학생 삭제(DES-04)는 학교에 영향이 없다. 학교 삭제는 학생을 지우지 않는다.

## 대안 분석

| 대안 | 장점 | 단점·위험 | 판단 |
|---|---|---|---|
| A. `school` 테이블 + 학생이 id로 참조 (선택) | 이름을 바꾸면 모든 학생에 반영된다. 삭제 시 "학교 비우기"가 FK 규칙 하나로 끝난다. 학생 수 집계가 정확하다 | 마이그레이션에 데이터 이관(텍스트 → id)이 필요하다. 학생 입력 필드가 바뀐다 | **채택** — "관리"에 이름 변경이 포함되고, 삭제 시 학교 비우기를 사용자가 골랐다 |
| B. `school` 테이블은 이름 목록만, 학생은 텍스트 그대로 | 학생 API·데이터가 그대로다. 마이그레이션이 테이블 추가뿐이다 | 학교 이름을 바꿔도 학생은 옛 이름으로 남는다. 삭제해도 학생의 학교가 비지 않아 사용자 결정과 어긋난다. 학생 수는 이름 일치로 세야 한다 | 기각 |
| C. 학교 목록을 `학원 설정`의 값 하나(JSON 목록)로 저장 | 테이블이 늘지 않는다 | B의 단점을 모두 가지며, 동시 수정 시 덮어쓰기 위험이 있다 | 기각 |

## 마이그레이션과 롤백

- **업그레이드(한 리비전):**
  1. `school` 테이블 생성.
  2. 캠퍼스별로 학생의 학교 값을 앞뒤 공백을 지우고 빈 값을 뺀 뒤 서로 다른 이름마다 학교 1건을 만든다(이름이 100자를 넘는 일은 없다 — 기존 열도 100자).
  3. `student.school_id`를 추가하고 같은 캠퍼스·같은 이름의 학교로 채운다.
  4. `student.school` 열을 지운다.
- **다운그레이드:** `student.school` 문자열 열을 다시 만들고 학교 이름으로 채운 뒤 `school_id`와 `school` 테이블을 지운다. 학교 이름은 학생에게 돌아오지만 **학생이 없는 학교는 사라진다.**
- **배포:** 스키마·데이터 이관이 있으므로 배포 전 `ops/backup.sh`로 백업한다. 웹과 API가 같은 이미지라 함께 바뀐다(구 웹이 새 API를 부르는 구간 없음).
- **롤백:** 이미지를 되돌리고 다운그레이드를 실행한다. 업그레이드 후 새로 만든 학교 중 학생이 없는 것은 잃는다 — 문제가 있으면 백업에서 복원한다.

## 검증 방법

- API: 학교 등록·이름순 목록·학생 수, 중복(공백 차이 포함)·빈 이름 거부, 이름 변경이 학생 출력 `school`에 반영, 삭제 시 학생 `school_id` NULL·다른 필드 보존·감사 로그, 다른 캠퍼스 학교 id로 학생 저장 시 422, 다른 캠퍼스 학교의 수정·삭제 403, 강사의 학교 API 403, 학생 목록이 학교 이름을 함께 반환(조회 횟수 고정), 마이그레이션 왕복(텍스트 → 학교 연결 → 텍스트 복원).
- 웹: [학교] 탭 등록·수정·삭제와 오류 표시, 강사에게 탭 숨김, 학생 등록 줄·수정 창의 학교 드롭다운 선택지와 POST·PATCH 본문의 `school_id`, 학교가 없을 때 안내·링크, 기존 학생 수정 창에 현재 학교가 선택되어 있음, VER-35(좁은 폭에서 페이지 넘침 없음).
- 배포 후: 테스트 운영에서 기존 학생 26명의 학교 열이 그대로 보이고 [학교] 탭에 3건·학생 수가 맞는지 확인.

## 남은 위험과 미해결 사항

- **학교 삭제는 확인 없이 바로 학생들의 학교를 비운다**(사용자 결정). 잘못 지우면 학교를 다시 만들고 학생마다 다시 골라야 한다. 목록의 학생 수가 지우기 전 판단 근거다.
- 같은 이름의 다른 학교(지역만 다름)는 구분할 수 없다 — 이름만 관리하기로 했으므로 필요하면 "○○고(수원)"처럼 이름에 넣는다.
- 학생 목록에서 학교를 바로 바꾸는 드롭다운, 학교로 학생 검색·거르기, 드롭다운에서 바로 새 학교 추가는 범위 밖이다. 필요해지면 별도로 요청한다.
