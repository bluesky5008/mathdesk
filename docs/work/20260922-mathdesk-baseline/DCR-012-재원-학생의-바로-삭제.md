## 요약

- 변경 분류: **요구사항 변경** — [DCR-006](./DCR-006-퇴원-비활성-학생과-반의-삭제.md)이 정한 학생 삭제의 선행 조건(퇴원)을 없앤다.
- 변경 요지: 원장은 **재원·휴원·퇴원 어느 상태의 학생이든** 목록 행의 [삭제]로 바로 삭제할 수 있다. 함께 지우는 범위, 미리보기, 이름 입력 확인, 원장 전용은 그대로다. 반 삭제(비활성 반만)는 바꾸지 않는다.
- 사용자 결정(2026-10-11): 클라이언트가 "삭제를 직관적으로" 하기를 원함 → 행 오른쪽 상담/퇴원/수정 옆에 [삭제]. 대상 범위로 "퇴원 학생 행에만"(권장)·"모든 행, 재원생은 퇴원 안내" 대신 **"모든 학생 바로 삭제"**를 골랐다.
- 사용자 재승인 결과: **승인 (2026-10-11)** — 기준선 `v12` → `v13` 발행

## 변경 사유와 증거

- **계기:** 클라이언트 요구 ③ "우측의 상담/퇴원/수정에 삭제 버튼 추가 — 삭제를 직관적으로 하고 싶다"(2026-10-11, 사용자 전달).
- **확인한 사실:**
  1. 지금은 [수정] 창 안에서만, 그것도 **퇴원으로 저장된 학생**일 때만 [삭제]가 보인다. 퇴원 학생은 기본 목록에서 빠져 있어 "퇴원 포함"을 켜고 → [수정] → [삭제]의 세 단계를 거친다.
  2. 서버도 같은 조건을 건다 — `deletion.py`의 `_student_blocker`가 퇴원이 아니면 `409`("먼저 퇴원 처리해 주세요"), 미리보기는 `deletable=false`.
  3. 삭제는 기록째 지운다(DCR-006): 보호자·반 배정·일일 기록·시험 응시·답안지 판독·발송 내역·상담 기록. 되돌리는 방법은 백업 복원뿐이다.
  4. **테스트 운영에는 자동 백업이 없다.** 배포 때마다 `ops/backup.sh`를 손으로 돌린 백업만 있다(`~/mathdesk-backups`, 마지막 2026-10-11 12:13). 운영 자동 백업은 [TASK-57](../../plan.md#task-57-운영-구성-준비)(대기)에 있다.
- **보류한 구현:** 없음. 같은 요청의 ①학년 ②상태 드롭다운은 기준선 안이라 [TASK-79](../../plan.md#task-79-학년상태-드롭다운)로 완료했고, ③은 코드를 쓰지 않았다.

## 기존 설계와 제안 설계

### 기존 (기준선 `v12`, DCR-006)

- 학생은 `퇴원`일 때만 삭제할 수 있다(1단계 안전장치). 아니면 `409`, 변경 없음.
- 삭제 전 미리보기(분류별 건수와 영향), 이름 입력 확인(2단계 안전장치), 원장 전용, 한 트랜잭션, 감사 로그 `student.delete`(대상 ID·분류별 건수, 이름 없음).
- 화면: [수정] 창의 [삭제] — 퇴원 학생만.

### 제안 (기준선 `v13`)

1. **선행 조건 제거(학생만):** 재원·휴원·퇴원 모두 원장이 삭제할 수 있다. 반은 그대로 비활성일 때만.
2. **그대로 두는 것:** 함께 지우는 범위와 남기는 것(OMR 원본 PDF), 미리보기, 이름 입력 확인, 원장 전용(강사 403), 캠퍼스 스코프, 한 트랜잭션·행 잠금, 감사 로그에 이름·연락처 미기록.
3. **잃는 안전장치를 메우는 것:**
   - 미리보기 창에서 재원·휴원 학생이면 경고를 먼저 보인다 — "재원 중인 학생입니다. 오늘 수업 명단과 일일 입력에서 바로 빠지고, 출결·성적 기록까지 모두 지워집니다."
   - 감사 로그 `student.delete`에 **삭제 당시 상태**(`enrolled`·`paused`·`withdrawn`)를 더한다. 재원생이 지워졌는지 나중에 확인할 수 있게 한다.
4. **화면:** 학생 목록 각 행의 상담/퇴원/수정 옆에 [삭제](원장만). [수정] 창의 [삭제]도 상태와 관계없이 보인다(원장만). 강사에게는 보이지 않는다.

|---|---|---|---|

## 대안 분석

| 대안 | 장점 | 단점·위험 | 판단 |
|---|---|---|---|
| A. 상태 무관 바로 삭제 (사용자 선택) | 한 번에 지운다. 입력 실수를 바로 정리한다 | 1단계 안전장치가 없어진다. 수업 중인 학생의 기록을 실수로 통째로 지울 수 있다 | **채택** — 이름 입력 확인은 그대로 두고 재원 경고·감사 로그 상태로 보완 |
| B. 퇴원 학생 행에만 [삭제] | 정책 그대로, DCR 불필요 | 퇴원 학생이 기본 목록에서 숨어 있어 여전히 찾아야 한다 | 사용자가 고르지 않음 |
| C. 모든 행에 [삭제], 재원생은 "먼저 퇴원" 안내 | 정책 그대로, 버튼은 늘 보인다 | 재원생은 두 번 처리해야 한다 | 사용자가 고르지 않음 |
| D. 재원생 [삭제] 시 "퇴원 + 삭제"를 한 창에서 | 기록상 퇴원을 거친다 | 결과는 A와 같고 창만 복잡해진다 | 기각 |

**ADR을 만들지 않는 이유:** 저장 방식·구조의 기술 결정이 아니라 "누가 언제 지울 수 있는가"라는 요구사항 조정이다(DCR-006과 같은 판단).

## 마이그레이션과 롤백

- **마이그레이션:** 없음.
- **롤백:** `_student_blocker`를 되돌리고 화면의 [삭제] 표시 조건을 퇴원으로 돌리면 기준선 `v12` 동작이다. **이미 지운 학생은 백업 복원으로만 되돌린다.**

## 검증 방법

- **API:** 재원·휴원 학생 미리보기 `deletable=true`·건수 정확, 이름 확인 후 `DELETE` 204와 DCR-006 범위 전체 삭제·다른 학생 불변(기존 퇴원 학생 테스트를 재원 학생으로도), 이름 불일치 422·불변, 강사 403, 활성 반 삭제는 여전히 409, 감사 로그에 상태 포함·이름 미포함. 외래키 누락 방지 테스트 유지.
- **웹:** 원장 화면의 모든 행에 [삭제], 강사 화면에 없음, 재원 학생 미리보기에 경고, 이름 입력 후 삭제 요청. VER-35(행 버튼 4개, 390px).

## 남은 위험과 미해결 사항

- **실수 삭제는 되돌릴 수 없다.** 수업 중인 학생 한 명을 잘못 지우면 그 학생의 출결·과제·성적·상담·발송 기록이 모두 사라진다. 이름 입력이 유일한 차단 장치다.
- **테스트 운영에 자동 백업이 없다.** 지금 데이터는 시험용이라 영향이 작지만, 운영 이관 전에 자동 백업(TASK-57)이 있어야 이 기능을 안전하게 쓸 수 있다.
- 백업과 OMR 원본 PDF에는 삭제한 학생 정보가 남는다(DCR-006과 같음).
