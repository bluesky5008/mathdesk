## 요약

- 결정: 실제 운영(Phase B)을 Kubernetes가 아니라 **클라이언트마다 하나씩 두는 AWS Lightsail 단일 서버(서울) + `docker compose` + Cloudflare 터널**로 한다. 서버·AWS 계정·도메인·문자·LLM 계정은 모두 클라이언트 명의이고, 개발자는 각 계정의 IAM 사용자로만 접근한다. 두 서버는 같은 저장소·같은 compose 파일을 쓰고 환경변수 한 벌만 다르다.
- 핵심 이유: 클라이언트 2명이 각자 따로 운영하고 데이터가 섞이면 안 되며, 규모(학생 160명·월 문자 5,500건·시험지 30건)가 단일 2GB 서버로 충분하다. 테스트 운영(ADR-008)과 같은 구성을 그대로 옮기므로 검증된 경로다.
- 주요 단점: 서버 한 대라 장애 시 자동 복구가 없고, 클라이언트 수만큼 서버를 따로 관리해야 한다.

## 배경

- 기준선 `v1`은 Phase B를 Kubernetes 전제로 "전환 가능성만 보장"하고 실제 배포를 범위 밖에 두었다. 테스트 운영(Phase A′)은 개발자 맥미니에서 합성 데이터로만 돌고 있다.
- 2026-10-11 사용자 확인: 클라이언트는 2명(밤·핑수)이며 **각자 따로 운영**한다. 두 사람 모두 AWS 계정을 만들고 IAM 사용자 `yongs`를 발급했다(작업 기록). 둘 다 원장이 아니고 사업자등록증이 없다.
- 2026-10-11 결정: 문자 발송 설정은 **서버마다 환경변수 한 벌**. 알리고는 학원 사업자 인증 경유(갈래 A). 터널은 클라이언트 Cloudflare 계정 안의 원격 관리형(토큰) 터널.
- 규모 추정(운영-이관-안내): 반 8개·학생 160명, 문자 월 5,500건, 시험지 분석 월 30건. 테스트 운영 유휴 메모리 app 235MB·postgres 70MB·cloudflared 53MB.

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| **A. 클라이언트별 Lightsail 단일 서버 + compose + 터널** | 테스트 운영과 같은 구성, 월 약 $12, 계정·데이터·비용이 클라이언트별로 완전히 분리, 고정 IP(문자 발송 서버 IP) | 자동 복구 없음, 서버 수만큼 운영 반복 |
| B. 서버 한 대에 두 클라이언트(캠퍼스 분리) | 운영 1회 | 데이터가 한 DB에 섞여 소유·비용·백업·인계가 얽힌다. 한쪽 장애가 다른 쪽에 번진다. 계정 명의를 누구로 할지 풀리지 않는다 |
| C. Kubernetes(EKS 등) | 기준선의 Phase B 전제, 자동 복구 | 월 비용이 수십 배, 운영 난도가 클라이언트 규모에 맞지 않는다 |
| D. 개발자 맥미니 계속 운영 | 비용 0 | 실제 개인정보를 개발자 집 장비에 두게 된다. 유동 IP, 정전·회선 장애, 인계 불가 |
| E. 관리형 PaaS(Fly.io·Render 등) | 배포 간단 | Chromium·OpenCV 이미지가 무겁고, 한국 리전·원화 결제·클라이언트 명의 계정 발급이 어렵다 |

## 결정

1. 클라이언트마다 **클라이언트 명의 AWS 계정**의 Lightsail 인스턴스 1대(서울, 2GB·2vCPU, 고정 IP, 자동 스냅샷 7개)를 둔다. 서버 안에 `postgres`·`app`·`cloudflared` 세 컨테이너가 `compose.prod.yaml`로 돈다.
2. 외부 경로는 **클라이언트 Cloudflare 계정의 원격 관리형 터널** 하나다. 호스트에 어떤 서비스 포트도 게시하지 않고, Lightsail 방화벽은 SSH만 연다.
3. 이미지는 **서버에서 공개 저장소를 clone해 빌드**한다. 교차 빌드·레지스트리를 두지 않는다. 두 서버는 같은 커밋을 쓴다.
4. 환경 차이는 `.env` 한 벌(도메인·터널 토큰, 초기 원장, 알리고, LLM 키, DB 비밀번호)뿐이다. 테스트 운영(맥미니)은 **스테이징**으로 남겨 모든 변경을 먼저 거친다.
5. 백업은 **클라이언트 계정 안에만** 둔다: 서버 안 일일 `pg_dump`+파일 묶음(14일 보관, 권한 600) + Lightsail 자동 스냅샷. 개발자 장비로 운영 백업을 복사하지 않는다.
6. 개발자 접근은 IAM `yongs`(MFA) + SSH 키이며, 인계 시 클라이언트가 회수할 수 있어야 한다. 비밀값은 서버 `.env`에만 있고 저장소·메신저에 두지 않는다.

## 이유

- 데이터 소유·비용·인계가 클라이언트 단위로 떨어진다. 한쪽을 종료해도 다른 쪽에 영향이 없다.
- ADR-008의 테스트 운영 구성을 그대로 쓰므로 새로 검증할 것이 터널 토큰 방식과 자동 백업뿐이다.
- 고정 IP는 알리고 발송 서버 IP 등록에 필요하다(맥미니 유동 IP 문제 해소).

## 결과와 감수할 단점

- 서버 장애 시 사람이 복구한다. 스냅샷·덤프 복원 절차를 문서화하고 TASK-59에서 리허설한다.
- 운영 절차(배포·백업 확인·OS 갱신)를 클라이언트 수만큼 반복한다. 절차서를 템플릿으로 써서 반복 비용을 줄인다.
- 실제 개인정보가 처음으로 저장된다. NFR-17의 "합성 데이터만" 조건을 테스트 운영에 한정하고 운영 데이터 보호 요구(NFR-20)를 신설한다(DCR-022).
