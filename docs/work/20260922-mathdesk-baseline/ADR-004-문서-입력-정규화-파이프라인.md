## 요약

- 결정: `.hwp`·`.hwpx`·`.pdf`·이미지 4종을 `DocumentIngest`가 `{pages, blocks(text|equation|image|table), page_images}` 공통 구조로 정규화한 뒤, 이후 단계(문항 분할·분석)는 원본 포맷을 알지 못하게 한다.
- 핵심 이유: 분석 코드가 포맷별로 분기하면 유지보수 비용이 4배가 되고 폴백 경로를 만들기 어렵다.
- 주요 단점: 포맷마다 표현력이 달라 정규화 과정에서 레이아웃 정보가 일부 손실된다.

## 배경

학원의 시험지는 대부분 한글 문서(`.hwp`)이며 PDF·스캔 이미지도 섞여 들어온다. `.hwp`는 OLE 복합문서 + 자체 바이너리 레코드라 오픈소스 파서의 재현율이 제한적이고, 수식은 LaTeX가 아닌 한글 수식 스크립트로 저장된다. 수식이 그림 개체로 삽입된 시험지는 텍스트 추출 자체가 불가능하다.

## 영향을 받는 요구사항과 제약

- [FR-27 시험지 업로드](../../requirements.md#fr-27-상세): 4종 포맷 수용.
- [AC-21](../../requirements.md#인수-조건): 암호가 걸린 `.hwp`는 오류 사유를 안내해야 한다.
- [RISK-02](../../requirements.md#위험): `.hwp` 파싱 품질 한계.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| A. 공통 구조로 정규화 후 단일 분석 경로 (선택) | 분석 코드 단일화, 폴백 삽입 용이 | 정규화 손실, 초기 설계 비용 | — |
| B. 포맷별 분석 경로 분리 | 포맷 고유 정보 최대 활용 | 코드 4중 분기, 테스트 4배 | 높음 |
| C. 모든 입력을 PDF로 먼저 변환 | 처리 경로 1개 | 변환기(한컴 COM 또는 LibreOffice+H2Orestart) 의존, 수식 재현율 저하 | 중간 |
| D. `.pdf`만 지원 | 가장 단순 | 사용자가 매번 변환해야 함, 요구 미충족 | 낮음 |

## 결정

1. `DocumentIngest.normalize(file_ref) -> NormalizedDocument` 하나를 계약으로 둔다.
2. 포맷별 구현: `.hwpx`는 OWPML XML 직접 파싱, `.hwp`는 텍스트·표·수식 스크립트 추출, `.pdf`는 텍스트 레이어·좌표·페이지 이미지 추출, 이미지는 페이지 이미지로 취급한다.
3. 텍스트 추출이 불가능하거나 비어 있으면 해당 페이지를 이미지 경로로 폴백 표시하고 후속 분석이 이미지 입력을 쓰게 한다.
4. 암호·배포 금지 문서는 파싱 실패로 처리하고 사용자에게 사유와 대안을 안내한다.
5. 한글 수식 스크립트는 변환하지 않고 원문 그대로 보존한다. LaTeX 변환 필요 여부는 [Q-11](../../design.md#가정과-미해결-질문)로 남긴다.
6. 시각 검수용 렌더링(`.hwp` → PDF)은 이번 범위에 포함하지 않으며, 필요해지면 별도 결정으로 다룬다.

## 이유

1. 문항 분할·분석은 입력 포맷과 무관한 로직이므로 경계를 정규화 지점에 두는 것이 자연스럽다.
2. 이미지 폴백을 공통 구조 안에 표현하면 수식 그림 문제와 스캔본 문제를 같은 방식으로 처리할 수 있다.
3. 변환기 의존(대안 C)은 Phase A의 실행 환경 요구를 크게 높인다.

## 결과와 감수할 단점

- 레이아웃·서식 정보가 정규화 과정에서 손실되어 일부 문항 분할이 부정확할 수 있다. 사용자 확정 단계(FR-29)로 보완한다.
- `.hwp`에서 수식이 그림인 경우 분석 품질이 이미지 경로 품질에 종속된다.
