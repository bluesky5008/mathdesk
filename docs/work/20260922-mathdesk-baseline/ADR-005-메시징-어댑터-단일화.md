## 요약

- 결정: SMS·LMS·MMS와 카카오 알림톡·친구톡을 알리고 API 하나로 처리하는 단일 `MessagingAdapter` 인터페이스를 두고, 기본 동작 모드를 테스트 모드로 한다.
- 핵심 이유: 알리고가 두 채널을 모두 제공하므로 어댑터를 분리하면 폴백 로직만 복잡해진다.
- 주요 단점: 메시징 공급자를 알리고에 결합시킨다.

## 배경

학부모 통보는 문자(SMS/LMS/MMS)와 카카오 알림톡 두 채널을 모두 쓴다. 알림톡은 템플릿 사전 심사가 필요하고 미친구·템플릿 불일치 시 실패하므로 문자 폴백이 현실적으로 필요하다. 알리고는 문자와 알림톡 API를 모두 제공한다.

## 영향을 받는 요구사항과 제약

- [FR-23 문자 발송과 로그](../../requirements.md#fr-23-상세): 테스트 모드 기본, 로그 스냅샷.
- [FR-38 알림톡 발송](../../requirements.md#기능-요구사항): 실패 시 SMS·LMS 대체 발송.
- [RISK-05](../../requirements.md#위험): 실발송·심사 지연으로 검증이 막힐 수 있다.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| A. 알리고 단일 어댑터 (선택) | 폴백 구현 단순, 잔여량·과금 조회 일원화 | 공급자 결합 | — |
| B. 채널별 어댑터 분리(문자/카카오) | 공급자 교체 유연 | 폴백 시 두 어댑터 조정 로직 필요, 로그 이원화 | 중간 |
| C. 범용 메시징 추상화(여러 공급자 플러그인) | 최대 유연성 | 지금 필요 없는 일반화, 구현량 증가 | 높음 |

## 결정

1. `MessagingAdapter.send(channel, recipients, body|template_id, vars, attachments) -> list[SendResult]`를 유일한 발송 계약으로 둔다.
2. 구현체는 알리고 구현과 테스트 모드 구현 두 가지이며, 기본 설정은 테스트 모드다.
3. 채널 선택(SMS/LMS/MMS)은 본문 길이와 첨부 유무를 기준으로 서버가 결정한다.
4. 알림톡 실패 시 설정에 따라 문자로 대체 발송하고 두 시도를 모두 `message_log`에 남긴다. 대체 성공은 `fallback_sent`로 기록한다.
5. 발송 결과는 수신자 단위로 기록하며 본문 스냅샷은 이후 원천 데이터가 바뀌어도 불변이다.

## 이유

1. 폴백이 같은 공급자 안에서 일어나므로 어댑터 1개가 결과·과금·로그를 일관되게 다룰 수 있다.
2. 테스트 모드를 기본값으로 두면 발신번호 등록과 템플릿 심사가 끝나기 전에도 M4·M8 개발과 검증을 진행할 수 있다.
3. 공급자 교체가 필요해지면 인터페이스는 그대로 두고 구현체만 추가하면 된다.

## 결과와 감수할 단점

- 알리고 고유의 파라미터가 인터페이스에 새어 들어올 위험이 있다. `vars`와 결과 타입을 공급자 중립으로 정의해 완화한다.
- 실발송 검증은 계정·발신번호 준비([Q-02](../../requirements.md#가정과-미해결-질문))에 의존한다.
