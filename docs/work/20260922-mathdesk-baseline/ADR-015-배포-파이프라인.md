## 요약

- 결정 대상: 개발(로컬) → 스테이징(맥미니 `mathdesk.yongs-wiki.com`) → 운영(밤·핑수 각자의 Lightsail 서버 2대)으로 코드가 흘러가는 길. 어디서 빌드하고, 무엇을 자동으로 돌리고, 사람이 어디서 승격을 누르고, 어떻게 되돌리는지.
- 제안: **이미지는 GitHub Actions가 한 번 만들어 GHCR에 올리고(amd64+arm64), 스테이징과 운영 서버는 같은 이미지를 pull만 한다. 승격은 사용자 장비에서 수동 명령(`ops/deploy.sh <대상> <태그>`)으로 하고, 그 명령 안에서 백업·pull·기동·헬스 확인을 자동으로 한다.** 운영 서버에 코드를 두지 않고 서버 접근 키를 GitHub에 두지 않는다.
- 바뀌는 것: [ADR-013](./ADR-013-운영-배포처-클라이언트별-Lightsail-단일-서버.md) 결정 3("서버에서 공개 저장소를 clone해 빌드, 교차 빌드·레지스트리를 두지 않음")을 이 ADR이 **대체**한다. 결정 1·2·4·5·6은 그대로다. DES-25의 "서버에서 이미지 빌드" 문구는 승인 시 DCR로 고친다.
- 사용자 결정 필요: 아래 [결정](#결정)의 ①~⑤.

## 배경

- 지금 배포는 맥미니에서 `docker compose -f compose.testops.yaml up -d --build`를 손으로 치는 것이고, CI는 없다. 테스트(API 325건·웹 201건)는 개발자가 로컬에서 돌린다.
- 운영은 클라이언트 2명(밤·핑수)이 각자의 AWS 계정에 Lightsail 2GB 서버 1대씩 둔다(ADR-013). 같은 코드가 **세 곳**(스테이징 1 + 운영 2)에 올라가야 하고, 운영 2곳은 같은 커밋이어야 한다.
- 아키텍처가 갈린다: 맥미니는 arm64, Lightsail은 amd64. 이미지는 1.73GB(Node 빌드 + uv + Chromium headless shell + 나눔 글꼴)다.
- ADR-013 결정 3은 "서버에서 clone해 빌드"였다. 그 뒤 확인된 사실: 2GB 서버에서 `npm ci`·Vite 빌드·`uv sync`·Playwright 설치를 돌리면 메모리가 빠듯해 스왑 2GB를 전제해야 하고(AWS 안내문 C단계), 같은 빌드를 서버마다 반복하며, 스테이징(arm64)과 운영(amd64)이 같은 커밋이어도 같은 바이너리가 아니다.
- 저장소는 공개(`bluesky5008/mathdesk`)다. 공개 저장소는 GitHub Actions 실행 시간과 GHCR 저장이 무료다. 이미지에는 `.env`·비밀값이 들어가지 않는다(Dockerfile 확인).
- 제약: 운영 서버 접근 키(SSH·IAM)는 클라이언트가 회수할 수 있어야 하고 저장소·메신저에 두지 않는다(ADR-013 결정 6, NFR-20).

## 고려한 대안

| 대안 | 빌드 위치 | 승격 트리거 | 장점 | 단점·위험 | 판단 |
|---|---|---|---|---|---|
| **A. 서버 빌드 + 수동 스크립트** (ADR-013 결정 3 유지, 스크립트만 추가) | 각 서버에서 `git clone` 후 빌드 | 사용자 장비에서 `ops/deploy.sh` → SSH → `git checkout <태그> && compose up --build` | 추가 인프라 0. 비밀값은 서버에만 | 2GB 서버 빌드 부하·시간(스왑 전제). 서버마다 빌드 반복(3회). 스테이징과 운영 바이너리 불일치. 빌드 실패 시 서버에서 원인 추적. 운영 서버에 소스 코드가 남음 | 기각 — 서버 수가 2가 되면서 반복 비용과 불일치가 커졌다 |
| **B. CI 빌드 이미지 + 수동 승격** (제안) | GitHub Actions가 태그마다 amd64+arm64 이미지를 GHCR에 게시 | 사용자 장비에서 `ops/deploy.sh <대상> <태그>` → SSH → `compose pull && up -d` | 서버는 pull만(자원·시간 절약, 2GB 여유). 세 곳이 **같은 이미지 digest**. 롤백 = 이전 태그 pull(수십 초). 테스트가 CI에서 돌아 배포 전 게이트. 운영 서버에 코드 없음 | GitHub Actions·GHCR 의존(장애 시 수동 빌드로 우회 가능). 이미지가 공개됨(공개 저장소 코드와 같은 내용, 비밀 없음). 워크플로 1개와 compose 2개 수정 | **채택** |
| **C. push 시 운영 자동 반영** (Actions가 SSH로 배포 또는 Watchtower) | B와 같음 | `main` push 또는 태그 push가 곧 운영 반영 | 손이 안 간다 | 클라이언트 운영 서버에 사람 확인 없이 반영(마이그레이션 포함). 서버 SSH 키를 GitHub Secrets에 보관 → 공개 저장소 쓰기 권한 = 운영 서버 권한. 백업 시점 통제 어려움. 변경이 잦은 지금 단계와 맞지 않음 | 기각 — 운영이 2곳뿐이고 스테이징 확인이 승격 조건이다 |
| D. 맥미니에서 교차 빌드 → `docker save \| ssh load` | 맥미니 buildx(amd64) | 수동 | 레지스트리 불필요 | 1.7GB를 서버마다 전송. 맥미니가 꺼져 있으면 배포 불가. ADR-013이 이미 교차 빌드를 배제 | 기각 |

## 결정

승인 시 다음이 기준선이 된다. ①~⑤는 사용자가 고른다(기본값은 굵게).

1. **빌드 위치** — **GitHub Actions**가 빌드한다. `main` push마다 테스트(pytest + vitest + `tsc`)와 빌드 검증을 돌리고, **릴리스 태그** push 때만 이미지를 `ghcr.io/bluesky5008/mathdesk`에 게시한다(amd64·arm64, 네이티브 러너 사용으로 QEMU 없이). 서버는 빌드하지 않는다.
2. **승격 방식** — **수동 명령.** `ops/deploy.sh <staging|bam|pingsu> <태그>`를 사용자 장비에서 실행한다. 스크립트는 ① 대상 서버에 SSH ② `ops/backup.sh`(운영만, 배포 전 백업) ③ `docker compose pull` ④ `up -d`(마이그레이션은 기동 시 `alembic upgrade head`, 기존 그대로) ⑤ `/api/health`와 이미지 태그 확인 ⑥ 실패 시 이전 태그로 되돌리는 명령을 출력. 스테이징은 로컬 실행(SSH 없음).
3. **승격 순서** — 스테이징에 먼저 올려 사용자가 확인한 태그만 운영에 올린다. 두 운영 서버는 같은 태그를 쓴다(한쪽만 먼저 올려 하루 두고 보는 것은 허용).
4. **버전 표기** — 릴리스 태그는 **`r<번호>`** 일련번호(`r1`, `r2`, …)로 한다. 문서 기준선(`v27`)과 섞이지 않게 `v`를 피한다. 이미지 태그 = git 태그. `main` push마다의 검증 빌드는 게시하지 않는다.
5. **스테이징도 같은 이미지** — `compose.testops.yaml`의 `build:`를 `image: ghcr.io/…:${MATHDESK_IMAGE_TAG}`로 바꾼다. 개발용 `compose.yaml`은 로컬 빌드를 유지한다(코드 수정 중 즉시 반영).
6. 서버에 두는 것 — `compose.prod.yaml`, `.env`, `ops/` 스크립트 사본뿐. 소스 저장소는 clone하지 않는다. 스크립트 사본은 `deploy.sh`가 `scp`로 함께 올린다.
7. 비밀값 — 운영 서버 SSH 키는 사용자 장비에만(ADR-013 결정 6 그대로). GitHub에는 비밀값을 두지 않는다(GHCR 게시는 `GITHUB_TOKEN`으로 충분). 운영 서버는 공개 이미지라 레지스트리 로그인도 필요 없다.
8. 롤백 — `ops/deploy.sh <대상> <이전 태그>`. 마이그레이션이 되돌릴 수 없는 변경을 포함한 릴리스는 태그 메모에 표시하고, 그 경우 롤백은 배포 전 백업 복원(`ops/restore.sh`)으로 한다.

## 이유

- 운영 2곳 + 스테이징 1곳이 **같은 digest**를 쓰면 "스테이징에서 확인한 것이 운영에 올라간다"가 말 그대로 성립한다. 서버 빌드로는 커밋만 같을 뿐이다.
- 2GB 서버가 빌드를 하지 않으면 스왑 전제가 빠지고, 배포 시간이 빌드(수 분) 대신 pull(수십 초)로 줄며, 빌드 실패가 운영 서버에서 일어나지 않는다.
- 승격을 수동으로 두면 서버 접근 키가 GitHub에 가지 않는다. 공개 저장소에서 "쓰기 권한 = 운영 서버 권한"이 되는 것을 피한다.
- 테스트를 CI에서 돌리면 "로컬에서 돌렸다"가 아니라 기록이 남는 게이트가 된다(지금은 로컬 실행 결과를 작업 기록에 손으로 적는다).
- 공개 저장소라 비용이 0이다. 비공개로 바뀌면 Actions 분·GHCR 용량이 과금 대상이 되지만 이 규모(월 수 회 빌드, 이미지 2GB 남짓)는 무료 한도 안이다.

## 결과와 감수할 단점

- GitHub가 멈추면 이미지를 못 만든다. 우회: 맥미니에서 `docker buildx --platform linux/amd64`로 빌드해 GHCR에 직접 push(개인 토큰 필요, 평소에는 쓰지 않음).
- 이미지가 공개된다. 코드가 이미 공개이므로 새로 드러나는 것은 없지만, 비공개 전환 시 패키지도 비공개로 바꿔야 하고 그러면 서버에 pull 토큰이 필요해진다.
- 배포 절차가 한 단계 늘어난다(태그 push → Actions 완료 대기 → 승격). 그 대신 서버에서 기다리는 빌드 시간이 없어진다.
- `compose.testops.yaml`이 빌드를 하지 않게 되므로, 맥미니에서 "지금 코드로 바로 올려 보기"는 `compose.yaml`(개발)로 한다.
