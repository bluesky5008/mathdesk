## 요약

- 결정 대상: 개발(로컬) → 스테이징(맥미니 `mathdesk.yongs-wiki.com`) → 운영(밤·핑수 각자의 Lightsail 서버 2대)으로 코드가 흘러가는 길. 어디서 빌드하고, 무엇을 자동으로 돌리고, 사람이 어디서 승격을 누르고, 어떻게 되돌리는지.
- 결정(사용자, 2026-10-17): **이미지는 GitHub Actions가 한 번 만들어 GHCR에 올리고(amd64) 스모크를 통과시킨다. 운영 반영은 Actions의 `workflow_dispatch`로 사용자가 명령할 때만 하며, 환경별 필수 승인자와 명령 제한 SSH 키로 잠근다. 스테이징(맥미니)은 지금처럼 로컬 빌드·수동 배포를 유지한다.** 운영 서버에 코드를 두지 않는다.
- 바뀌는 것: [ADR-013](./ADR-013-운영-배포처-클라이언트별-Lightsail-단일-서버.md) 결정 3("서버에서 공개 저장소를 clone해 빌드, 교차 빌드·레지스트리를 두지 않음")을 이 ADR이 **대체**한다. 결정 1·2·4·5·6은 그대로다. DES-25의 "서버에서 이미지 빌드" 문구는 승인 시 DCR로 고친다.
- 사용자 승인(2026-10-17): 이 ADR과 DCR-027이 함께 승인되어 기준선 `v28`이 발행되었다. ADR-013 결정 3은 이 ADR이 대체한다.

## 배경

- 지금 배포는 맥미니에서 `docker compose -f compose.testops.yaml up -d --build`를 손으로 치는 것이고, CI는 없다. 테스트(API 325건·웹 201건)는 개발자가 로컬에서 돌린다.
- 운영은 클라이언트 2명(밤·핑수)이 각자의 AWS 계정에 Lightsail 2GB 서버 1대씩 둔다(ADR-013). 같은 코드가 **세 곳**(스테이징 1 + 운영 2)에 올라가야 하고, 운영 2곳은 같은 커밋이어야 한다.
- 아키텍처가 갈린다: 맥미니는 arm64, Lightsail은 amd64. 이미지는 1.73GB(Node 빌드 + uv + Chromium headless shell + 나눔 글꼴)다.
- ADR-013 결정 3은 "서버에서 clone해 빌드"였다. 그 뒤 확인된 사실: 2GB 서버에서 `npm ci`·Vite 빌드·`uv sync`·Playwright 설치를 돌리면 메모리가 빠듯해 스왑 2GB를 전제해야 하고(AWS 안내문 C단계), 같은 빌드를 서버마다 반복하며, 스테이징(arm64)과 운영(amd64)이 같은 커밋이어도 같은 바이너리가 아니다.
- 저장소는 공개(`bluesky5008/mathdesk`)다. 공개 저장소는 GitHub Actions 실행 시간과 GHCR 저장이 무료다. 이미지에는 `.env`·비밀값이 들어가지 않는다(Dockerfile 확인).
- 제약: 운영 서버 접근 키(SSH·IAM)는 클라이언트가 회수할 수 있어야 하고 저장소·메신저에 두지 않는다(ADR-013 결정 6, NFR-20).

| **A. 서버 빌드 + 수동 스크립트** (ADR-013 결정 3 유지, 스크립트만 추가) | 각 서버에서 `git clone` 후 빌드 | 사용자 장비에서 `ops/deploy.sh` → SSH → `git checkout <태그> && compose up --build` | 추가 인프라 0. 비밀값은 서버에만 | 2GB 서버 빌드 부하·시간(스왑 전제). 서버마다 빌드 반복(3회). 스테이징과 운영 바이너리 불일치. 빌드 실패 시 서버에서 원인 추적. 운영 서버에 소스 코드가 남음 | 기각 — 서버 수가 2가 되면서 반복 비용과 불일치가 커졌다 |

## 결정

사용자 결정(2026-10-17): 빌드 위치 ① GitHub Actions, 승격 ② Actions가 반영하되 **사용자 명령(`workflow_dispatch`)일 때만**, 태그 ③ 날짜형, 스테이징 ④ 맥미니 수동 로컬 빌드 유지. 아래가 기준선이 된다.

1. **빌드** — `main` push와 PR마다 CI(`ci.yml`)가 테스트(pytest + Postgres 서비스 컨테이너, vitest, `tsc -b` 빌드)를 돌린다. 릴리스 태그 push 때 `release.yml`이 **amd64 이미지 하나**를 `ghcr.io/bluesky5008/mathdesk:<태그>`로 게시한다(스테이징이 CI 이미지를 쓰지 않으므로 arm64는 만들지 않는다).
2. **이미지 스모크** — `release.yml`은 게시한 이미지를 Postgres와 함께 띄워 `alembic upgrade head`·`/api/health`·초기 원장 로그인을 확인한다. 통과한 태그만 배포 대상이다(통과 표시: `:<태그>-verified` 꼬리표).
3. **운영 승격** — `deploy.yml`은 `workflow_dispatch` 전용(입력: 대상 `bam`·`pingsu`·`both`, 태그). push로는 돌지 않는다. 대상마다 GitHub **환경**(`bam`, `pingsu`)을 두고 **필수 승인자 = 사용자**로 잠근다. 잡은 ① `-verified` 꼬리표 확인 ② 환경 비밀값의 SSH 키로 서버 접속 ③ 서버의 `ops/deploy.sh <태그>` 실행(백업 → `compose pull` → `up -d` → `/api/health`·이미지 태그 확인) ④ 실패 시 잡 실패로 멈추고 이전 태그를 로그에 남긴다. 두 운영 서버는 같은 태그를 쓴다(한쪽 먼저 올려 두고 보는 것은 허용).
4. **서버 키** — 서버에 배포 전용 계정(`deploy`, docker 그룹)을 두고 `authorized_keys`에 `command="~/mathdesk/ops/deploy.sh"`·`no-pty`·`no-port-forwarding`을 붙여 **그 키로는 배포 스크립트만** 실행된다. 키는 GitHub 환경 비밀값과 사용자 장비에만 있다. 클라이언트는 서버에서 `deploy` 계정의 키를 지워 회수할 수 있다(ADR-013 결정 6 유지).
5. **태그** — `YYYY.MM.DD`(예: `2026.10.17`), 같은 날 두 번째부터 `-2`, `-3`. git 태그 = 이미지 태그. 문서 기준선 `v27`과 섞이지 않는다.
6. **스테이징** — 맥미니 `compose.testops.yaml`은 지금처럼 **로컬 빌드·수동 배포**를 유지한다(TASK마다 즉시 배포하는 리듬 보존). 운영 릴리스는 스테이징에서 확인한 커밋에 태그를 붙여 시작한다.
7. **서버에 두는 것** — `compose.prod.yaml`, `.env`, `ops/` 스크립트 사본. 소스 저장소는 clone하지 않는다. 스크립트 갱신은 배포 잡이 `scp`로 함께 올린다.
8. **롤백** — 같은 `deploy.yml`을 이전 태그로 실행. 되돌릴 수 없는 마이그레이션이 든 릴리스는 태그 메모에 표시하고 그 경우 배포 전 백업 복원(`ops/restore.sh`)으로 되돌린다.
9. **개발** — 로컬 `compose.yaml`은 로컬 빌드 그대로.
10. **워크플로 보안 규칙**(사용자 질의 2026-10-17에 대한 답으로 결정) — ① 배포·릴리스 잡은 **서드파티 액션을 쓰지 않는다**(`ssh`·`docker`·`gh` 명령 직접 사용). GitHub 소유 액션(`actions/checkout` 등)만 쓰고 **커밋 SHA로 고정**한다 ② `pull_request_target` 트리거를 쓰지 않는다(포크 PR에 비밀값이 전달되는 예외 경로) ③ 배포 잡은 `GITHUB_TOKEN` 권한을 `packages: read`로 최소화하고 환경 비밀값은 SSH 키 하나뿐이다 ④ 쓰기 권한 보유자는 사용자 1인을 유지하고 GitHub 계정은 2단계 인증(패스키)을 쓴다 ⑤ 서버 `deploy.sh`는 `ghcr.io/bluesky5008/mathdesk`에 존재하고 `-verified` 꼬리표가 있는 태그만 받는다. 이로써 키가 유출되더라도 가능한 행위는 "검증된 태그 재배포·백업 실행"으로 한정되고 셸·데이터 접근은 불가하다.

## 이유

- 운영 2곳 + 스테이징 1곳이 **같은 digest**를 쓰면 "스테이징에서 확인한 것이 운영에 올라간다"가 말 그대로 성립한다. 서버 빌드로는 커밋만 같을 뿐이다.
- 2GB 서버가 빌드를 하지 않으면 스왑 전제가 빠지고, 배포 시간이 빌드(수 분) 대신 pull(수십 초)로 줄며, 빌드 실패가 운영 서버에서 일어나지 않는다.
- 승격을 `workflow_dispatch` + 환경 승인으로 두면 push가 운영을 건드리지 못하고, 배포·백업·헬스 결과가 Actions 로그 한곳에 남는다. 서버 키는 환경 비밀값에만 노출되고 `command=` 제한으로 배포 스크립트 외에는 쓸 수 없다. 저장소 쓰기 권한은 현재 사용자 1인이다.
- 스테이징을 로컬 빌드로 유지하는 대신 CI 이미지 스모크로 운영 산출물 자체를 검증한다. 최근 7일 스테이징 배포 21회(하루 최대 9회)라 태그·CI 대기를 끼우면 리듬이 깨진다.
- 테스트를 CI에서 돌리면 "로컬에서 돌렸다"가 아니라 기록이 남는 게이트가 된다(지금은 로컬 실행 결과를 작업 기록에 손으로 적는다).
- 공개 저장소라 비용이 0이다. 비공개로 바뀌면 Actions 분·GHCR 용량이 과금 대상이 되지만 이 규모(월 수 회 빌드, 이미지 2GB 남짓)는 무료 한도 안이다.

## 결과와 감수할 단점

- GitHub가 멈추면 이미지를 못 만든다. 우회: 맥미니에서 `docker buildx --platform linux/amd64`로 빌드해 GHCR에 직접 push(개인 토큰 필요, 평소에는 쓰지 않음).
- 이미지가 공개된다. 코드가 이미 공개이므로 새로 드러나는 것은 없지만, 비공개 전환 시 패키지도 비공개로 바꿔야 하고 그러면 서버에 pull 토큰이 필요해진다.
- 운영 릴리스 절차가 늘어난다(태그 push → 릴리스 워크플로 대기 → 배포 워크플로 실행·승인). 그 대신 서버에서 기다리는 빌드 시간이 없어진다.
- 스테이징(arm64 로컬 빌드)과 운영(amd64 CI 이미지)은 같은 커밋이지만 같은 바이너리는 아니다. 네이티브 휠·Chromium 차이로 생기는 문제는 이미지 스모크와 운영 배포 후 헬스 확인으로 잡는다.
- 서버 SSH 키 하나가 GitHub에 있다. 유출돼도 `command=` 제한으로 배포 스크립트만 실행되며, 클라이언트가 서버에서 키를 지우면 회수된다.
